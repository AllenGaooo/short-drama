# 消息中间件「旁路」降级隐患 —— RocketMQ 不可用导致核心写入失败

> 模块：`service-drama`
> 问题等级：**高**（MQ 故障会拖垮短剧核心 CRUD）
> 状态：✅ 已修复
> 发现时间：2026-09-08（本地联调时 RocketMQ 未启动，暴露此问题）

---

## 一、隐患概述

`service-drama` 在创建/更新/删除短剧后，会发送 `drama-sync` 消息通知搜索服务更新 ES 索引。

但消息发送**没有做异常保护**：一旦 RocketMQ（NameServer 9876）不可用，`sendDramaSync()` 抛出的异常会向上冒泡，导致**短剧本身的创建/修改/删除全部失败**。

即：**搜索索引同步（旁路功能）的故障，拖垮了短剧核心写入（主流程）**。

---

## 二、问题代码（修复前）

### 2.1 消息生产者（无异常保护）

**文件**：`service-drama/src/main/java/com/bunny/flix/drama/mq/DramaSyncProducer.java`

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class DramaSyncProducer {

    private static final String TOPIC = "drama-sync";
    private final RocketMQTemplate rocketMQTemplate;

    public void sendDramaSync(DramaDTO dramaDTO) {
        log.info("发送短剧同步消息: dramaId={}", dramaDTO.getId());
        rocketMQTemplate.convertAndSend(TOPIC, dramaDTO);   // ← ❌ 无 try/catch，MQ 挂了直接抛异常
    }
}
```

## 三、影响链路（为什么严重）

```
RocketMQ 不可用（NameServer 9876 连不上）
   │
   ▼ RocketMQTemplate.convertAndSend() 抛出异常
DramaSyncProducer.sendDramaSync()  → 异常向上抛
   │
   ▼
DramaServiceImpl.createDrama()  → 方法中断
   │
   ▼
DramaController.create()  → 返回 500
   │
   ▼
【业务后果】运营无法新增/编辑/下架短剧
         —— 尽管 MySQL 完全正常！
```

### 故障表现（实际日志）

```
2026-09-08 19:13:20  RocketmqRemoting : closeChannel: close the connection to remote address[127.0.0.1:9876]
2026-09-08 19:13:23  RocketmqRemoting : closeChannel: ...   ← 反复重连失败
2026-09-08 19:13:26  RocketmqRemoting : closeChannel: ...
```

此时调用 `POST /api/drama` 会直接 500，而不是"创建成功但索引稍后同步"。

### 设计原则违背

消息通知属于**旁路（side path）**，不是主流程的强依赖。正确做法是：

> **旁路故障不应该阻断主流程。**

这与我在其他服务中遵循的原则一致：
- 播放服务：埋点/进度上报失败不影响用户观看
- 搜索服务：缓存/ES 故障降级返回空，不阻断搜索页
- Agent 服务：RAG/工具调用失败降级，仍返回回复

## 四、修复方案

### 4.1 修复后代码

**文件**：`service-drama/.../mq/DramaSyncProducer.java`

```java
/**
 * 发送短剧同步消息（同步到搜索服务更新 ES 索引）
 *
 * ⚠️ 必须做异常降级：
 *    MQ 属于"旁路"，不是主流程依赖。若 NameServer 不可用导致这里抛异常，
 *    会让 createDrama / updateDrama / deleteDrama 全部失败——
 *    即"搜索索引同步故障"拖垮"短剧核心写入"，这是不可接受的。
 *    因此发送失败只记录日志，由定时任务全量重建索引兜底最终一致。
 */
public void sendDramaSync(DramaDTO dramaDTO) {
    try {
        rocketMQTemplate.convertAndSend(TOPIC, dramaDTO);
        log.info("发送短剧同步消息成功: dramaId={}", dramaDTO.getId());
    } catch (Exception e) {
        log.error("发送短剧同步消息失败 dramaId={}，索引同步将延迟（由全量重建任务兜底）: {}",
                dramaDTO.getId(), e.getMessage());
    }
}
```

### 4.2 修复效果

| 场景 | 修复前 | 修复后 |
|---|---|---|
| RocketMQ 正常 | 发送成功，索引同步 | 不变 ✅ |
| RocketMQ 故障 | **创建短剧 500 失败** | 创建成功，索引延迟（记 error 日志）✅ |

业务方（运营）在 MQ 故障期间仍能正常维护短剧，只是搜索结果暂时不更新。

## 五、数据一致性如何保证

降级后消息丢失了，索引不一致怎么办？靠**三层兜底**：

| 层级 | 机制 |
|---|---|
| 1 | **MQ 重试**：RocketMQ 自身重试（若仅是瞬时抖动） |
| 2 | **消费者幂等**：搜索服务 `DramaSyncConsumer` 用版本号 + SETNX 去重，重复投递安全 |
| 3 | **全量重建**：定时任务全量扫 MySQL 重建 ES 索引（**生产必备**，兜住所有漏网之鱼） |

> 建议：为 `service-search` 增加一个凌晨执行的全量重建任务，扫描 `t_drama` 全量写入 ES。这是最终一致性的最后一道防线。

## 七、延伸：旁路降级通用原则

项目中所有"非主流程依赖"都应做降级，汇总如下：

| 服务 | 旁路依赖 | 降级策略 |
|---|---|---|
| `service-drama` | RocketMQ 索引同步 | ✅ 已修复：失败只记日志，全量重建兜底 |
| `service-video` | 进度上报、埋点事件 | 失败只记日志，不影响播放 |
| `service-search` | Redis 缓存、ES | Redis 挂了降级查库；ES 故障返回空列表 |
| `bunny-flix-agent` | RAG 检索、MCP 工具 | 失败返回空列表/error，仍生成回复 |
| `service-id-generator` | Redis 统计 | 统计失败不影响发号 |

**判断标准**：问自己"这个依赖挂了，用户还能完成核心操作吗？"
- 能 → 做降级（try/catch + 兜底）
- 不能（如数据库主库）→ 才是真正的强依赖，必须告警而非静默

## 八、面试话术

> "我在联调时发现一个隐患：短剧服务创建/修改后会发 MQ 通知搜索服务更新索引，但发送没做异常保护。这意味着 RocketMQ 一挂，**创建短剧就直接 500** —— 搜索索引同步这个旁路功能，把核心写入给拖垮了。
>
> 我的修复是给消息发送加异常降级：MQ 属于旁路不是主流程强依赖，发送失败只记日志，保证运营在 MQ 故障期间仍能正常维护短剧；索引的一致性靠三层兜底——MQ 重试、消费端幂等、以及定时任务全量重建。
>
> 后来我把这个原则推广到整个项目：判断一个依赖是不是强依赖，就问'它挂了用户还能不能完成核心操作'，能的话就必须降级。"

**追问：为什么不直接用 try/catch 吞掉就完事？**
→ 因为要保证最终一致：必须有全量重建任务兜底，否则消息丢了索引就永久不一致了。降级不是"不管了"，而是"换一条路达成目标"。
