# 短剧播放管理服务 —— 逐句拆解（流程 + 代码支撑）

> 模块：`service-video`（端口 8300，播放域 `com.bunny.flix.video.play`）
> 存储：Redis（实时态）+ MySQL（持久态）分层
> 每句给出：**业务含义 → 处理流程 → 代码支撑（精确到方法/行号）→ 面试话术**

## 第 1 句

> **「负责剧集查询、播放进度、观看记录等核心播放业务开发，针对短剧业务高读流量场景采用 Redis + MySQL 分层存储」**

### 业务含义
播放是核心链路，读远大于写（海量用户看少量热门剧）。用**分层存储**：热/实时数据放 Redis，持久数据放 MySQL。

### 处理流程
```
【写】播放进度上报（每 5 秒）
   → Redis（实时态）  watch:{userId}:{episodeId}
   → RocketMQ        异步批量落库
   → MySQL（持久态）  drama_watch_record

【读】播放入口
   → Redis 查热点剧集（命中直接返回）
   → 未命中 → 查 MySQL/短剧服务 → 回写 Redis
   → Redis 查续播位置（断点续播）
```

### 代码支撑

**① 实时态（Redis）** — `WatchProgressService` 第 24 行
```java
private static final String WATCH_KEY_PREFIX = "watch:";
// Key: watch:{userId}:{episodeId}
// Value: Hash {position, duration, episodeId, dramaId, updateTime}
```

**② 持久态（MySQL）** — `WatchRecord` 实体 → `drama_watch_record` 表
建表：`sql/drama_play.sql`（含 `uk_user_episode` 唯一索引，保证 upsert 幂等）

**③ 剧集查询（分层）** — `PlayServiceImpl.authorizePlay()` 第 50 行
```java

EpisodeDTO episode = dramaCacheService.getDetailWithLogicalExpire(episodeId,
        () -> fetchEpisode(episodeId), EpisodeDTO.class);
// 2) 续播位置从 Redis 读
Integer lastPosition = watchProgressService.getLastPosition(userId, episodeId);
// 3) 视频地址从 MySQL 查（转码完成的 HLS 地址）
Video video = findVideo(episodeId);
```

**④ 分层职责表**

| 数据类型 | Redis（实时/热） | MySQL（持久） |
|---|---|---|
| 播放进度 | ✅ `watch:{userId}:{episodeId}` | ✅ `drama_watch_record`（异步落库） |
| 剧集信息 | ✅ `drama:detail:{id}` | ✅ `t_video` / 短剧服务 |
| 播放凭证 | ✅ `play:token:*` | ❌ 无需持久化 |
| 观看记录 | ❌ | ✅ `drama_watch_record` |

### 面试话术
> "播放是典型的**高读低写**场景，所以我用分层存储：进度这种高频写、允许少量丢失的实时数据放 Redis；观看记录这种要持久化的放 MySQL，中间用 MQ 异步批量同步。剧集信息这种热点读，也用 Redis 挡在前面。"

## 第 3 句

> **「用户播放进度优先写入 Redis，通过 RocketMQ 异步批量同步 MySQL，降低高频播放行为对数据库产生的写压力」**

### 业务含义
**问题**：100 万用户 × 每 5 秒上报 = 20 万 QPS 写库，行锁争用严重。

**方案**：进度只写 Redis → 发 MQ → 消费端**攒批**批量写 MySQL。

### 处理流程
```
客户端每 5 秒 → POST /api/play/progress
   │
   ├─1 写 Redis（Hash，实时态）        WatchProgressService 第 35 行
   └─2 发 MQ（PLAY_PROGRESS 事件）     PlayEventService.sendEvent()
                 │
                 ▼ RocketMQ topic: play-event
        ProgressSyncConsumer.onMessage()
                 │  攒批：满 100 条 或 每 5 秒
                 ▼ 批量 upsert MySQL
           drama_watch_record
```

### 代码支撑

**① 写 Redis（优先）** — `WatchProgressService.reportProgress()` 第 35 行
```java
redisTemplate.opsForHash().put(key, "position", String.valueOf(position));
redisTemplate.opsForHash().put(key, "duration", String.valueOf(duration));
redisTemplate.expire(key, WATCH_TTL_DAYS, TimeUnit.DAYS);
// 同时投递进度事件
playEventService.sendEvent(userId, dramaId, episodeId, PLAY_PROGRESS, position, duration, null);
```

**② 发 MQ** — `PlayEventService.sendEvent()`
```java
rocketMQTemplate.convertAndSend("play-event", JSONUtil.toJsonStr(event));
// 失败只记日志，绝不影响播放主流程
```

**③ 批量消费落库** — `ProgressSyncConsumer`
```java
// 攒批策略 1：缓冲区满 100 条立即落库
synchronized (buffer) {
    buffer.add(record);
    if (buffer.size() >= BATCH_SIZE) flush();
}

// 攒批策略 2：每 5 秒定时 flush（低峰期也能及时入库）
@Scheduled(fixedDelay = 5000)
public void scheduledFlush() { ... }

// 批量 upsert
private void flush() {
    for (WatchRecord r : batch) upsert(r);
}
```

**④ 服务关闭兜底** — `@PreDestroy destroy()` 落库剩余数据

**⑤ 兜底补偿** — `WatchRecordSyncTask`（定时任务，处理 MQ 丢失的极端情况）

### 面试话术
> "进度上报如果直接写库，百万用户每 5 秒一次就是 20 万 QPS 写压力，行锁争用会很严重。所以我的方案是：进度**只写 Redis**，同时发一条 MQ 消息；消费端**攒批**——满 100 条或每 5 秒批量 upsert 一次，把高频写转成低频批量写，数据库压力降低两个数量级。另外还有个定时任务做兜底补偿，处理 MQ 消息丢失的极端情况。"

**追问：这样数据会丢吗？**
→ 允许少量丢失（宕机时最多丢一个批次），这是**取舍**：观看进度是可容忍少量丢失的数据，用可用性换性能。不想丢可以缩短 flush 间隔。

## 第 4 句

> **「针对热点剧集缓存瞬时失效造成大量请求访问数据库的问题，采用逻辑过期、异步重建及限流机制进行保护」**

### 业务含义
**问题（缓存击穿）**：热点 Key 失效瞬间，海量并发同时回源，打垮数据库。

**方案三层**：
1. **逻辑过期** —— 热点数据不设真 TTL，过期判断放 value 内
2. **异步重建** —— 过期后单线程重建，其余请求返回旧值（永不阻塞）
3. **限流** —— Sentinel 兜底，超阈值直接拒绝

### 处理流程
```
请求热点剧集
  │
  ▼ 读缓存（无真 TTL，永不真正过期）
命中且未逻辑过期 → 直接返回
  │
命中但已逻辑过期 → 抢锁
     ├─ 抢到 → 提交异步线程重建缓存，本次先返回旧值
     └─ 没抢到 → 直接返回旧值（不阻塞）
  │
  ▼ 兜底：Sentinel 限流（QPS 超阈值 → 429）
```

### 代码支撑

**① 逻辑过期实现** — `DramaCacheService.getDetailWithLogicalExpire()`
```java
// 1. 缓存值内嵌逻辑过期时间
public static class LogicalCacheValue {
    private Object data;
    private long expireAt;
    public boolean isExpired() { return System.currentTimeMillis() >= expireAt; }
}

// 2. 已逻辑过期：抢锁后异步重建，本次返回旧值
if (value.isExpired()) {
    if (tryLock(lockKey)) {
        rebuildExecutor.submit(() -> {
            T fresh = loader.get();
            safeSet(key, JSONUtil.toJsonStr(LogicalCacheValue.of(fresh, DETAIL_TTL_MINUTES)), ...);
        });
    }
    return data;   // ← 无论抢没抢到锁，都返回旧值，不阻塞
}
```

**② 异步重建线程池**
```java
private final ExecutorService rebuildExecutor = Executors.newFixedThreadPool(4, r -> {
    Thread t = new Thread(r, "drama-cache-rebuild");
    t.setDaemon(true);
    return t;
});
```

**③ 互斥锁（另一套方案，非热点用）** — `getDetail()` 第 48 行 + `tryLock()` 第 95 行
```java
Boolean ok = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, "1", LOCK_TTL_SECONDS, TimeUnit.SECONDS);
```
未抢到锁：等待重试读缓存（第 76-77 行，50ms × 20 次）

**④ 限流保护** — `SentinelConfig.initRules()`
```java
rules.add(rule("play:authorize", authorizeQps));   // 默认 50000
rules.add(rule("play:progress", progressQps));
rules.add(rule("play:event", eventQps));
```
配合 `PlayController` 的 `@SentinelResource(blockHandler = "authorizeBlockHandler")`

**⑤ 降级策略** — `PlayController.authorizeBlockHandler()`
```java
return Result.error(429, "当前观看人数过多，请稍后重试");
// 进度上报被限流则直接丢弃（进度允许丢失，不影响观看）
return Result.success("limited");
```

### 面试话术
> "缓存击穿是热点 Key 失效瞬间海量请求同时回源。我用**逻辑过期**解决：热点数据不设真正的 Redis TTL，而是把过期时间放在 value 里面；过期后由一个线程**异步重建**，其他请求继续返回旧值，做到永不阻塞、永不断流。另外用 Sentinel 做兜底限流，超阈值直接返回 429。"

**追问：逻辑过期和互斥锁怎么选？**
→ 互斥锁：数据一定最新，但等待期间线程阻塞；逻辑过期：永不阻塞，代价是短暂返回旧值。**热点剧集用逻辑过期**（百万并发不能等），普通数据用互斥锁。

**追问：为什么 Redis TTL 设成逻辑 TTL 的 2 倍？**
→ 逻辑过期模式下 key 不依赖 TTL 触发失效，Redis TTL 只是兜底清理；设 2 倍保证"已过期但异步重建未完成"时数据不被清掉。

## 第 5 句

> **「视频文件通过 CDN/对象存储进行分发，Java 服务主要负责播放权限、剧集信息、播放进度及观看记录管理」**

### 业务含义
**职责边界**：视频流本身不经过 Java 服务（走 CDN），Java 只管"业务元数据 + 权限"。这是重要的架构认知——**不让大流量穿透应用服务器**。

### 处理流程
```
1. 客户端请求播放 → Java 服务
2. Java：查剧集 + 校验权限 + 生成防盗链 Token
3. 返回 CDN 地址（带 token & expire）
4. 客户端直连 CDN 拉 HLS 流（不经过 Java 服务）
```

### 代码支撑


**② 剧集信息** — `fetchEpisode()` 第 98 行（Feign 调 service-drama）+ `findVideo()` 第 131 行（查转码状态）

**③ CDN 地址 + 防盗链** — `resolvePlayUrl()` 第 149 行

**④ 播放进度 & 观看记录** — `WatchProgressService`（Redis）+ `ProgressSyncConsumer`（落库）

- `index.m3u8` + 多个 `.ts` 分片
- 支持分片加载（边下边播）、断点续播、CDN 缓存友好、动态码率

### 面试话术
> "这里有个关键的**职责边界**：视频流本身不经过 Java 服务，客户端拿到地址后直连 CDN 拉 HLS 流。Java 服务只负责播放权限校验、剧集信息、播放地址和进度记录——这样大流量不会穿透应用服务器。视频地址也不是裸传的，会带一个临时 token 做防盗链，token 用 MD5 对用户 ID、剧集 ID、过期时间和密钥签名，过期或被篡改都播不了。"

## 七、面试必记的 4 个"取舍"

| 取舍 | 说明 |
|---|---|
| **进度允许少量丢失** | 用可用性换性能；宕机最多丢一个批次。要更可靠就缩短 flush 间隔 |
| **逻辑过期短暂返回旧值** | 用数据新鲜度换"永不阻塞"；热点场景必须这么选 |
| **进度上报被限流直接丢弃** | 进度丢了不影响观看；但播放入口不能丢，要返回明确 429 |
| **降级不返回兜底地址** | Token 生成失败就明确报错，绝不返回无签名地址（会造成盗链） |
