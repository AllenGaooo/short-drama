# 兔兔短剧平台 —— 业务背景梳理

> 本文从「业务为什么需要」的角度梳理各服务，用于回答面试官的
> **「你为什么做这个项目」「它解决什么业务问题」**。
> 技术实现细节见 `面试.md`，本文只讲业务驱动力。

---

## 一、平台业务背景（总纲）

**行业与用户特征**：短剧 APP 行业快速发展，用户观看习惯向**碎片化、沉浸式**内容消费转变——单次观看时长短、频次高、连续刷剧。

**平台的两类诉求**：

| 诉求 | 具体内容 |
|---|---|
| **技术侧** | 支持海量用户**同时观看视频**，保证低延迟、高可用 |
| **业务侧** | 结合**金币激励、广告变现、用户成长**等运营玩法提升用户留存 |

**这决定了整体架构取向**：播放是核心链路（高并发、高实时），搜索与推荐是流量入口（体验、转化），金币与行为采集是留存手段（运营玩法的数据基础）。

---

## 二、各服务的业务背景（业务痛点 → 技术目标）

### 1. 分布式 ID 生成服务（service-id-generator）

**业务背景**
平台业务数据种类多：订单、用户、短剧、剧集、评论、支付流水等，且各业务服务**多实例部署**。

**业务痛点**
- 数据库自增主键在多实例高并发写入下存在**性能瓶颈**（自增锁争用）
- 平台规划了**分库分表**，各分片本地自增会产生**主键冲突**

**技术目标**
为全平台提供**统一、全局唯一、趋势递增、高性能**的主键发放能力，让业务服务不关心 ID 怎么来的。

---

### 2. 短剧播放微服务（service-video / Drama Play Service）

**业务背景**
播放是**核心营收链路**。海量用户同时观看，同时要承载金币激励、行为分析等运营玩法。

**业务痛点**
- **盗链风险**：视频地址直接返回给用户，可被复制传播，造成带宽成本与版权损失
- **进度写入压力**：百万用户每 5 秒上报一次观看进度，直接写库是巨量写压力
- **行为数据要复用**：播放、完成等行为要驱动推荐、画像、金币、统计等多个下游
- **突发流量**：热门剧上线会带来播放请求尖峰

**技术目标**
- 播放链路独立成服务：播放鉴权、地址管理、进度记录、行为采集、事件分发
- 支撑高并发观看，同时把行为数据异步广播给各业务方

---

### 3. 短剧搜索服务（service-search）

**业务背景**
内容平台中，**搜索是用户找剧的主要入口**，搜索体验直接影响内容分发效率与用户留存。

**业务痛点**
- 数据量增长后，数据库 `LIKE` 查询无法满足性能与相关性要求
- 中文检索需要分词，且要支持剧名、演员、题材、标签**多字段**检索
- 用户还要按题材、标签、热度**筛选与排序**
- 短剧上下架后，搜索索引需要及时同步

**技术目标**
提供全文检索、多条件筛选、相关性排序能力，并保证**搜索性能**与**索引数据的最终一致**。

---

### 4. 短剧 AI 对话服务（agent / mcp / rag / aigateway / graph）

**业务背景**
短剧内容海量，用户常面临**"不知道看什么"**的选择困难；同时运营希望用更自然的方式提升转化与留存。

**业务痛点**
- 传统搜索要求用户**主动输入准确关键词**，长尾需求（「重生逆袭类爽文」）难以满足
- 用户是**连续追问**的（「上一部」「类似刚才那部」），单轮问答无法承接
- 短剧知识散落在简介、角色、题材、标签中，缺少统一的语义检索能力
- 找剧、看详情、看榜单这些能力分散，用户要在多个页面间切换

**技术目标**
- 用**对话**替代关键词搜索，降低用户表达成本
- **意图识别 + 工具调用**：把搜索、详情、榜单、推荐封装为工具，由 Agent 按意图动态调用
- **多轮上下文**：支持指代表达，实现连续交互
- **RAG 知识库**：把短剧内容向量化，实现语义检索

---

### 5. 金币服务（service-coin）

**业务背景**
金币激励是提升用户留存的核心运营玩法——用户看剧获得金币，形成正向循环。

**业务痛点**
- 看剧奖励**重复发放**（MQ 重复投递、用户重复触发）会造成资损
- 用户可能**刷金币**，需要限额

**技术目标**
消费播放完成事件自动发放奖励，并保证**幂等**（不重复发）与**限额**（防刷）。

## 三、业务闭环（串联所有服务）

讲业务背景时，能把这个闭环说出来，说明你有**全局视角**而不只是写某个模块：

```
用户注册（ID 服务分配用户ID）
   │
   ├─► 找剧：搜索服务（关键词检索）
   │         或 AI 对话（自然语言 + 多轮追问）
   │
   ▼
播放（播放服务：鉴权 → CDN 地址 → HLS 流）
   │
   ├─► 观看进度   → Redis 实时记录 → 定时批量落库
   ├─► 行为事件   → RocketMQ → 推荐服务（更新画像）
   │                        → 金币服务（看剧奖励）
   │                        → 数据统计
   ▼
推荐/搜索结果更精准 → 用户继续看 → 留存提升
```

**一句话概括业务价值**：
> 前三个服务（ID、播放、搜索）保障**核心链路的高并发与体验**，后两个（AI 对话、金币）承载**用户增长与留存**的运营玩法。

## 四、面试怎么讲业务背景（话术）

### 开场版（30 秒）

> 这个项目是一个短剧 APP 的后端，行业特点是用户观看**碎片化、高频次**，所以技术上要支撑**海量用户同时观看**，业务上要靠**金币激励、用户成长**这些玩法提升留存。
>
> 我负责的部分主要集中在两块：一块是**播放链路**，包括播放鉴权、进度同步、行为采集；另一块是**AI 对话找剧**，用 Agent 把搜索、推荐、知识检索串起来，让用户用自然语言就能找到想看的剧。另外还做了分布式 ID 生成服务，给各业务提供统一主键。

### 被问「为什么做这个项目」时

按 **业务痛点 → 我的方案 → 业务价值** 三段式答：

| 项目 | 业务痛点 | 业务价值 |
|---|---|---|
| ID 生成 | 多实例自增瓶颈、分库分表主键冲突 | 业务服务不用关心 ID 生成，支撑后续水平扩展 |
| 播放服务 | 盗链、进度写压力大、行为数据要复用 | 支撑高并发观看，行为数据驱动推荐与运营 |
| 搜索服务 | 数据量大查不动、中文分词、索引同步 | 提升内容分发效率，直接影响留存 |
| AI 对话 | 用户不知道看什么、关键词搜索门槛高、要连续追问 | 降低找剧成本，提升转化与留存 |
| 金币服务 | 重复发币资损、刷金币 | 保障激励玩法正确运行 |

## 五、⚠️ 讲业务背景的注意事项

1. **数据要能自圆其说**：如果说了"百万用户""千万级数据"，要准备好"你怎么知道的""怎么验证的"。没实测过就用"设计目标""规划中"这类表述。

2. **区分"已做"和"规划"**：
   - 分库分表是**规划中的能力支撑**，不是已落地的分库分表
   - 广告变现、用户成长是**运营玩法背景**，平台有规划，但不在我实现范围内

3. **业务背景要落到你做的事上**：讲完背景要立刻接"所以我做了……"，避免变成泛泛的行业分析。
