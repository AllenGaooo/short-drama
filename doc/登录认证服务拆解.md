## 第 1 句

> **「基于 Spring Security + JWT 实现手机号注册、登录、密码修改及个人信息管理」**

### 业务含义
用户体系的四个基本能力：注册、登录（密码/验证码）、改密码、维护个人信息。

### 处理流程
```
注册：手机号查重 → ID服务取号 → 生成盐 → MD5(密码+盐) → 落库
登录（密码）：查用户 → MD5(密码+盐)比对 → 生成 JWT
登录（验证码）：校验 Redis 验证码 → 生成 JWT
改密码：校验旧密码 → 生成新盐 → 加密新密码 → 落库 → 失效缓存
个人信息：查缓存 → 未命中查库 → 回写缓存
```

### ⚠️ 与描述的差距 & 面试话术

**实际未使用 Spring Security**，是自研 `common-security`（jjwt + 网关过滤器）。

> **面试说法**："认证这块我没有直接用 Spring Security，而是基于 jjwt 做了轻量实现。原因是我们的鉴权逻辑集中在网关（见第 2 句），业务服务只需要解析请求头里的用户上下文，用不上 Spring Security 完整的过滤器链和 `UserDetails` 体系——引入反而会增加每个服务的启动开销和配置复杂度。密码存储用的是 MD5 加盐。"

**注意**：如果面试官追问密码安全，要承认 MD5 已不推荐：
> "MD5 加盐是项目早期选型，生产应该换成 **BCrypt/Argon2** 这类自适应哈希算法。这点我记在优化清单里了。"

## 第 2 句

> **「将 Token 校验、用户身份解析等公共能力前置至 Gateway，通过请求头透传用户上下文，减少业务服务重复鉴权」**

### 业务含义
**问题**：如果每个微服务各自校验 Token，会造成：
- 每个服务都要引入 JWT 依赖、写一遍校验逻辑（重复代码）
- 密钥分散在各服务，安全性差
- 校验逻辑变更要改所有服务

**方案**：网关统一校验，解析出用户信息放请求头，下游直接用。

### 处理流程
```
请求 → Gateway(8080)
   │
   ▼ AuthGlobalFilter.filter()   ← 核心
   ├─1 白名单判断（登录/注册/搜索/Agent 免鉴权）
   ├─2 提取 Bearer Token
   ├─3 jwtUtils.validateToken(token) 校验
   ├─4 解析 userId/phone/userType
   └─5 request.mutate().header("X-User-Id", ...) 透传
   │
   ▼ 业务服务
   UserContext Filter 读头 → 存入 ThreadLocal
   │
   ▼ 业务代码 UserContext.getUserId() 直接取用户
```

### 代码支撑

**① 网关过滤器** — `AuthGlobalFilter`（`GlobalFilter, Ordered`）
```java
@Override
public int getOrder() { return -100; }   // 优先级最高，最先执行
```

**② 白名单** — `WHITE_LIST`
```java
"/api/user/login", "/api/user/sms", "/api/user/register",
"/api/admin/login", "/api/admin/register",
"/api/search", "/api/recommend/hot",
"/api/agent"        // 智能助手免登录
```

**③ Token 提取与校验**
```java
String token = extractToken(request);          // 去 "Bearer " 前缀
if (!jwtUtils.validateToken(token)) {
    return unauthorized(exchange, "Token已过期，请重新登录");
}
```

**④ 请求头透传（关键）**
```java
ServerHttpRequest mutatedRequest = request.mutate()
        .header("X-User-Id", String.valueOf(userId))
        .header("X-User-Phone", phone != null ? phone : "")
        .header("X-User-Type", userType != null ? userType : "user")
        .build();
return chain.filter(exchange.mutate().request(mutatedRequest).build());
```

**⑤ 下游还原上下文** — 各服务的 `XxxContextFilter`
```java
String userIdHeader = httpRequest.getHeader("X-User-Id");
if (userIdHeader != null && !userIdHeader.isEmpty()) {
    UserContext userContext = new UserContext();
    userContext.setUserId(Long.valueOf(userIdHeader));
    UserContext.set(userContext);       // 存入 ThreadLocal
}
try {
    chain.doFilter(request, response);
} finally {
    UserContext.remove();               // ★ 必须清理，否则线程复用导致用户串号
}
```
已接入：`service-video/VideoContextFilter`、`bunny-flix-agent/AgentContextFilter`、`service-coin/CoinContextFilter`、`bunny-flix-aigateway`、`service-admin/AdminContextFilter`

**⑥ ThreadLocal 上下文** — `common-security/UserContext`
```java
private static final ThreadLocal<UserContext> CONTEXT = new ThreadLocal<>();
public static Long getUserId() {
    UserContext context = CONTEXT.get();
    return context != null ? context.userId : null;   // 直接读字段，避开 Lombok getter 递归
}
```

### 面试话术
> "我把 Token 校验和用户身份解析都**前置到网关**：网关统一校验 JWT，解析出用户 ID、手机号，通过 `X-User-Id` 请求头透传给下游。各业务服务只需要一个过滤器把请求头还原到 ThreadLocal 的 `UserContext`，业务代码直接 `getUserId()` 就能拿到当前用户，不用每个服务重复写鉴权逻辑、也不用每个服务都持有密钥。"

**追问：为什么必须在 finally 里 remove？**
→ Web 服务器线程池复用线程，不清理会导致**下一个请求拿到上一个用户的身份**（用户串号），这是严重事故。

**追问：UserContext 那个"直接读字段"为什么？**
→ 之前踩过坑：静态方法 `getUserId()` 和 Lombok `@Data` 生成的实例 getter 同名，在静态方法里调 `context.getUserId()` 会解析成自身递归，导致 **StackOverflowError**。改成直接读字段 `context.userId` 解决。

## 第 3 句

> **「使用 Redis 缓存验证码、用户热点信息等高频数据，缓存命中率达到 95%+，降低 MySQL 查询压力」**

### 业务含义
验证码（高频读写、短生命周期）和热点用户信息（高频读）放 Redis，减少数据库访问。

### 处理流程

**验证码**：
```
发送：限流校验（60秒内不能重发）→ 生成验证码 → 存 Redis(5分钟) → 设置发送间隔标记
校验：从 Redis 取 → 比对 → 校验成功删除（一次性）
```

**用户热点信息**：
```
查询：查缓存 user:info:{userId} → 命中返回
     → 未命中查 MySQL → 回写缓存(30分钟+抖动)
更新：资料/密码/VIP 变更 → 失效缓存
```

### 代码支撑

**① 验证码缓存** — `SmsServiceImpl`
| 能力 | 行号 | 说明 |
|---|---|---|
| 发送间隔限流 | 第 34、47 行 | 60 秒内不能重复发送 |
| 存验证码 | 第 44 行 | TTL 5 分钟（第 26 行常量） |
| 校验验证码 | 第 54-56 行 | 从 Redis 取并比对 |
| 校验后删除 | 第 67 行 | **一次性**，防止重放 |

**② 用户热点信息缓存** — `UserServiceImpl`（本次补齐）
```java
// 缓存 key 与 TTL
private static final String USER_CACHE_PREFIX = "user:info:";
private static final long USER_CACHE_TTL_MINUTES = 30;

// 查询：三级（缓存 → DB → 回写）
public User getUserById(Long userId) {
    cacheQueryCount.incrementAndGet();
    User cached = getFromCache(userId);       // 1) 查缓存
    if (cached != null) return cached;
    User user = userMapper.selectById(userId); // 2) 查库
    ...
    putToCache(userId, user);                  // 3) 回写
    return user;
}
```

**③ TTL 抖动防雪崩**
```java
long ttl = USER_CACHE_TTL_MINUTES + (long) (Math.random() * 5);   // 30 + 0~5 分钟
```

**④ 缓存失效（一致性保证）**
```java
evictCache(userId);   // 改密码（第 257 行）、VIP 变更（第 275 行）后调用
```

**⑤ 降级** — Redis 异常时 try/catch，降级查库，**不阻断业务**

**⑥ 命中率可观测** — `cacheMetrics()`
```java
m.put("hitRate", Math.round(rate * 100.0) / 100.0 + "%");
```
统计点：`cacheQueryCount`（每次查询累加）、`cacheHitCount`（命中累加）

### ⚠️ 「95%+ 命中率」需要实测

**面试安全说法**：
> "验证码和热点用户信息走 Redis，热点用户缓存命中率我做了统计接口，压测后实际是 XX%（填真实值）。命中率上不去的话可以调大 TTL，或者对活跃用户做预热。"

**为什么理论上能到 95%+**（可以讲这个逻辑）：
- 登录后的用户会连续操作（看剧、评论、查信息），同一用户短周期内被反复查询
- 缓存 TTL 30 分钟，覆盖一次活跃的会话周期
- 用户信息是典型的**读多写少**（资料变更频率远低于查询频率）

### 面试话术
> "高频数据我用 Redis 缓存了两类：一类是**验证码**，自带 5 分钟过期，校验成功就删除保证一次性，还加了 60 秒发送间隔限流防刷；另一类是**热点用户信息**，用 Cache-Aside 策略，查的时候先查缓存、没有再查库并回写，TTL 30 分钟加随机抖动防雪崩，改密码或 VIP 变更时主动失效缓存保证一致性。Redis 挂了会降级查库，不影响业务。"

## 五、面试必记的 3 个"坑"

| 坑 | 说明 |
|---|---|
| **ThreadLocal 必须 remove** | 线程池复用线程，不清理会导致**用户串号**（A 看到 B 的数据） |
| **Lombok getter 与静态方法同名 → StackOverflow** | `UserContext` 上 `@Data` 生成实例 `getUserId()`，与静态方法同名；静态方法里调 `context.getUserId()` 会无限递归。改为直接读字段 |
| **改密码必须失效缓存** | 否则会返回旧密码的缓存数据（我已处理，第 257 行） |
