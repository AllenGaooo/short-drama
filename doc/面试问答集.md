## 2. 介绍一下项目的业务流程，系统能实现哪些功能（业务角度）

> 面试官要的是**业务闭环**，不是技术名词堆砌。讲"用户怎么用、平台靠什么赚钱"。

### 平台定位
短剧 APP，用户观看习惯**碎片化、高频次、连续刷剧**。技术侧要支撑海量用户同时观看，业务侧靠**金币激励、广告变现、会员/用户成长**提升留存。

### 核心业务流程（一个用户从进入到留存）

```
① 注册/登录（手机号+密码 或 验证码）
        ↓
② 找剧：搜索（关键词） 或 AI 对话（自然语言、多轮追问） 或 分类/榜单浏览
        ↓
③ 播放：拉起剧集 → 校验权限 → 拿带防盗链的播放地址 → CDN 拉 HLS 流
        ↓
④ 观看过程：每 5 秒上报进度（断点续播）、采集播放行为
        ↓
⑤ 看完一集：发放金币奖励（幂等防重复）
        ↓
⑥ 行为数据回流：更新用户画像 → 推荐更精准 → 用户继续看（留存提升）
```

### 系统功能模块

| 模块 | 面向 | 业务功能 |
|---|---|---|
| **用户/认证** | C 端 | 注册、登录、改密、个人资料；网关统一鉴权 |
| **短剧内容** | C 端 | 短剧/剧集/演员/分类标签管理与浏览 |
| **搜索** | C 端 | 全文检索、多条件筛选、相关性排序、热门榜单 |
| **播放** | C 端 | 播放鉴权、CDN 地址、观看进度、断点续播、行为采集 |
| **AI 对话** | C 端 | 自然语言找剧、意图识别、工具调用、多轮上下文 |
| **金币/营销** | 运营 | 看剧发金币、优惠券领取（Lua 防超卖）、签到任务 |
| **推荐** | C 端 | 个性化推荐、热门推荐、用户画像 |
| **后台管理** | 运营 | 短剧上下架、用户管理、优惠券发放、菜单权限 |

### 一句话概括业务价值
> 前几个模块（认证、内容、搜索、播放）保障**核心链路的体验与高并发**；金币、营销、推荐承载**用户增长与留存**的运营玩法。

## 3. 说一下搜索功能怎么实现的

> 详细拆解见 `搜索服务拆解.md`，这里给面试可直接说的版本。

### 索引设计（Mapping）
- 中文分词用 **IK 插件**：索引 `ik_max_word`（细粒度，提高召回），查询 `ik_smart`（粗粒度，提高精度）
- 给 `tags`、`actors`、`category` 加 **`keyword` 子字段** → 才能做精确筛选/聚合（text 字段无法 term 查询）
- 分片数设为 3（单分片过大拖慢查询）；`refresh_interval: 5s` 提升写入吞吐

### 查询实现

**1. 全文检索**：`multi_match(best_fields)` 跨字段带权重
```json
"fields": ["title^3.0", "description^1.5", "actors^1.2", "tags^1.2"]
+ minimumShouldMatch("75%")   // 过滤低质量召回
```

**2. 多条件筛选**：放 `filter` 上下文（题材/标签/播放量）
> 不参与算分，且 ES 会缓存 filter 结果，比 must 性能更好

**3. 相关性排序**：`function_score`
> 把 `heatScore`、`playCount` 用 **Log1p** 平滑后加到相关度得分上 → "相关度 + 热度" 混合排序

**为什么用 Log1p**：播放量从几千到几千万差异极大，线性加权会让热度**完全压倒相关度**；取对数后热度只作为温和加分项。

### 性能与一致性
- **性能**：Redis 缓存热点搜索结果（空值缓存防穿透、互斥锁防击穿）+ 慢查询告警守护 150ms 目标
- **一致性**：MySQL → MQ → Search → ES 最终一致（见问题 4、5）

### 面试话术
> "搜索我用 ES 做，中文分词用 IK——索引细粒度提高召回、查询粗粒度提高精度。查询用 multi_match 跨字段带权重，筛选条件放 filter 上下文因为它不算分还能被缓存。排序我没简单按时间倒序，而是用 function_score 把热度做 Log1p 平滑后加到相关度上。"

## 4. ES 的数据如何同步到 MySQL 中？

> ⚠️ **先澄清方向**：生产上通常是 **MySQL → ES 单向同步**，ES 是**检索副本**，不回写 MySQL。

### 为什么 ES 不回写 MySQL
- **MySQL 是权威数据源（Source of Truth）**：所有写操作以 DB 为准
- **ES 只用于检索**：不承载业务写入，ES 故障不影响业务
- ES 存的是**宽表/冗余数据**（为检索性能做了反规范化），回写会污染主数据

### 本项目的同步链路（MySQL → ES）

```
MySQL 数据变更（短剧创建/修改/下架）
   │
   ▼ DramaSyncProducer 发送 DramaDTO
RocketMQ  topic: drama-sync
   │
   ▼ DramaSyncConsumer 消费
   ├─1 版本号校验（updateTime 比对，丢弃乱序旧消息）
   ├─2 Redis SETNX 去重（拦截重复投递）
   ├─3 写入/删除 ES 索引 drama
   └─4 失效 Redis 缓存（search:q:*、排行榜）
```

代码：`service-drama/.../mq/DramaSyncProducer.java`、`service-search/.../mq/DramaSyncConsumer.java`

### 如果确实需要 ES → MySQL（极少数场景）
比如从 ES 聚合出统计数据回写：应走**独立的数据统计服务**，且只写**派生表/统计表**，绝不回写业务主表。

## 5. 数据同步可能会出现哪些问题？如何解决？

| # | 问题 | 原因 | 解决方案 |
|---|---|---|---|
| 1 | **消息丢失** | MQ 宕机、网络抖动 | ①RocketMQ 持久化+重试；②发送失败清去重标记允许重投；③**定时任务全量重建 ES 索引**兜底 |
| 2 | **消息乱序** | MQ 不保证全局顺序，旧消息后到 | 消费端**版本号校验**：记录已处理的最新 `updateTime`，旧消息直接丢弃（防旧数据覆盖新数据） |
| 3 | **重复消费** | MQ 重投、消费者重启 | ①Redis SETNX 去重；②ES 按 doc id 覆盖写本身幂等；③数据库唯一索引兜底 |
| 4 | **消费失败导致堆积** | 异常抛出 → MQ 无限重试（默认 16 次） | 消费端 **catch 所有异常只记日志**，配合重试与死信队列；绝不因个别消息阻塞整体 |
| 5 | **旁路拖垮主流程** | 发送 MQ 异常冒泡 | **发送必须降级**（try/catch），MQ 是旁路不是强依赖 —— 详见 `消息中间件旁路降级隐患.md` |
| 6 | **长期数据不一致** | 上述异常累积 | **全量重建任务**：凌晨全量扫 MySQL 重建 ES，是保证最终一致的最后防线（生产必备） |
| 7 | **缓存与索引不一致** | 索引更新了但缓存没失效 | 同步成功后主动失效缓存 `evictByPrefix("search:q:")` |

### 面试话术
> "同步问题我主要防三类：丢失、乱序、重复。丢失靠 MQ 重试加定时全量重建兜底；乱序靠版本号——消费端记录已处理的最新 updateTime，旧消息直接丢，否则会用旧数据覆盖新数据；重复靠 SETNX 去重，加上 ES 按 ID 覆盖写本身幂等。
>
> 还有个容易忽略的点：发送消息必须做异常降级。我踩过坑——原来发送没加 try/catch，RocketMQ 一挂，创建短剧直接 500 了，等于索引同步这个旁路把核心写入拖垮了。"

## 6. ES 中如何修改已经存入数据的字段类型？

> ⚠️ **核心结论：ES 不支持直接修改已有字段的 mapping 类型。**

### 为什么不能改
倒排索引一旦建立，字段类型就固化了。比如 `views` 是 `long`，改成 `text` 会导致已索引数据无法按新类型解析，查询报错或结果错误。

### 正确做法：重建索引（Reindex）

```bash
# 1. 新建目标索引，定义正确的 mapping
PUT /drama_v2
{ "mappings": { "properties": { "views": { "type": "text" } } } }

# 2. 把旧索引数据迁移到新索引
POST /_reindex
{ "source": { "index": "drama" }, "dest": { "index": "drama_v2" } }

# 3. 用别名切换，保证业务零停机
POST /_aliases
{ "actions": [
    { "remove": { "index": "drama",    "alias": "drama_alias" } },
    { "add":    { "index": "drama_v2", "alias": "drama_alias" } }
]}

# 4. 确认无误后删除旧索引
DELETE /drama
```

**别名（alias）是关键**：业务代码一直用 `drama_alias` 查询，重建时用别名切换，做到**零停机改字段类型**。

### 可以"不用重建"的有限情况

| 操作 | 是否允许 |
|---|---|
| 新增字段 | ✅ 允许（新字段自动加入 mapping） |
| 修改字段类型 | ❌ 必须 reindex |
| 修改分词器 | ❌ 必须 reindex |
| 增加 `keyword` 子字段 | ✅ 允许，但**已有数据不生效**，需 reindex 才能查到 |

### 本项目的注意点
我们给 `tags/actors` 加了 `keyword` 子字段做精确筛选——**存量老数据必须 reindex 才能让 keyword 字段生效**，否则按 `tags.keyword` 筛选历史数据会查不到。

## 7. 多级缓存怎么使用的？解决了什么业务问题？

### 缓存层次

```
L1 浏览器/CDN      ← 静态资源、视频流、图片
   ↓
L2 Redis 分布式缓存 ← 热点数据（跨实例共享）
   ↓
L3 JVM 本地缓存     ← 极高频、允许实例间不共享（如 ID 号段）
   ↓
L4 MySQL / ES
```

### 各层的实际落点

| 层次 | 缓存内容 | 位置 | 解决的业务问题 |
|---|---|---|---|
| **CDN** | 视频 HLS 切片、剧集图片 | 边缘节点 | 大流量不穿透应用服务器 |
| **Redis** | 热点剧集详情 `drama:detail:{id}` | `service-video/DramaCacheService` | 百万并发看同一部剧，DB 压力近乎为零 |
| **Redis** | 搜索结果 `search:q:*`、排行榜 | `service-search/SearchCacheService` | 搜索接口 RT 达标 |
| **Redis** | 观看进度 `watch:{userId}:{episodeId}` | `service-video/WatchProgressService` | 每 5 秒上报不直接写库 |
| **Redis** | 验证码、用户信息 | `service-user` | 降低高频查询的 DB 压力 |
| **JVM 本地** | ID 号段（Segment） | `service-id-generator/SegmentBuffer` | **发号零网络开销**，达万级 QPS |

### 解决的三大缓存问题

| 问题 | 场景 | 解法 |
|---|---|---|
| **缓存穿透** | 查不存在的数据，每次都打 DB | 空值缓存（`__EMPTY__`，短 TTL） |
| **缓存击穿** | 热点 Key 失效瞬间海量并发回源 | 互斥锁 / **逻辑过期 + 异步重建** |
| **缓存雪崩** | 大量 Key 同时失效 | TTL 加随机抖动 |

### 面试话术
> "多级缓存我按数据热度分层：静态资源和视频走 CDN；热点剧集详情、搜索结果、观看进度走 Redis；ID 号段这种极高频且允许实例间不共享的数据，直接放 JVM 本地内存——因为号段在 DB 里是互斥分配的，本地缓存不会导致重复，却能做到发号零网络开销。
>
> 热点数据我用逻辑过期：过期时间放在 value 里，过期后单线程异步重建，其他请求继续返回旧值，永不阻塞。"

## 8. Lua 脚本怎么用的？

### 为什么用 Lua
**保证多个 Redis 命令的原子性**。Redis 单线程执行 Lua，脚本执行期间不会被其他命令插入 —— 解决"判断 + 修改"的并发竞态。

### 本项目落点：优惠券领取（防超卖 + 幂等）

**文件**：`service-marketing/.../service/impl/CouponServiceImpl.java`

```java
// Lua：原子扣减库存 + 幂等校验（第 37 行）
private static final String DEDUCT_STOCK_LUA = """
        local stockKey = KEYS[1]
        local receivedKey = KEYS[2]
        local userId = ARGV[1]

        -- 幂等：已领取过直接返回 -1
        if redis.call('SISMEMBER', receivedKey, userId) == 1 then
            return -1
        end
        -- （后续为库存判断与扣减、SADD 标记已领取）
        """;

// 执行（第 76-77 行）
DefaultRedisScript<Long> script = new DefaultRedisScript<>(DEDUCT_STOCK_LUA, Long.class);
Long result = redisTemplate.execute(script, List.of(stockKey, receivedKey), userId.toString());

if (result == -1) throw new BusinessException("您已领取过该优惠券");
if (result == 0)  throw new BusinessException(ResultCode.COUPON_STOCK_EMPTY);
```

### 解决什么问题

| 不用 Lua 的问题 | Lua 如何解决 |
|---|---|
| `GET` 判断已领 → `SADD` 标记，两步之间可能被并发插入 → **重复领取** | 脚本内完成校验+扣减，**原子执行** |
| 先 `DECR` 再判断 → 可能扣成**负数（超卖）** | 脚本内先判断库存再扣减 |

### 为什么不用 Redis 事务（MULTI/EXEC）
Redis 事务**没有条件判断能力**（不能根据前一步结果决定下一步），而库存场景必须先判断再扣减；Lua 可以写 if/else，且同样原子。

### 面试话术
> "Lua 我用在优惠券领取：把'判断是否已领取'和'扣减库存'写在一个脚本里。Redis 执行 Lua 是单线程原子的，能保证这两步之间不被其他请求插入，避免重复领取和超卖。
>
> 没有用 Redis 事务是因为事务不支持条件判断——它不能根据前一步结果决定下一步，而库存场景必须先判断再扣减，Lua 更合适。"

**注意**：Lua 脚本要**短小**，避免长时间阻塞 Redis（Redis 单线程）。

## 9. Java 集合的分类以及具体有哪些集合

### 整体分类

```
Collection（单列）
├── List（有序、可重复、有索引）
│   ├── ArrayList      → 数组，查快增删慢，最常用
│   ├── LinkedList     → 双向链表，增删快查慢，可作队列/栈
│   └── Vector         → 数组，线程安全（方法 synchronized），已基本弃用
│       └── Stack      → 继承 Vector，栈
│
├── Set（无序、不可重复）
│   ├── HashSet            → 哈希表，最快，无序
│   │   └── LinkedHashSet  → 哈希表+链表，保持插入顺序
│   ├── TreeSet            → 红黑树，自动排序
│   └── EnumSet            → 枚举专用，位向量实现，极高效
│
└── Queue（队列）
    ├── ArrayDeque              → 数组双端队列，作栈/队列比 Stack 快
    ├── PriorityQueue           → 堆，优先级队列（小顶堆）
    ├── ArrayBlockingQueue      → 有界阻塞队列（数组）
    ├── LinkedBlockingQueue     → 可选有界阻塞队列（链表）
    ├── ConcurrentLinkedQueue   → 无锁并发队列（CAS）
    ├── SynchronousQueue        → 不存储元素，直接移交
    └── DelayQueue              → 延迟队列（订单超时、定时任务）

Map（双列 key-value，不属于 Collection）
├── HashMap            → 哈希表，允许 null key/value
│   └── LinkedHashMap  → 保持插入顺序，可实现 LRU 缓存
├── TreeMap            → 红黑树，按 key 排序
├── Hashtable          → 线程安全（全表锁），已弃用
├── ConcurrentHashMap  → 并发安全（CAS + 节点锁），最常用
└── ConcurrentSkipListMap → 跳表，并发有序
```

### 高频对比（面试必考）

| 对比 | 结论 |
|---|---|
| **ArrayList vs LinkedList** | 查询多/尾部增删 → ArrayList；中间频繁增删 → LinkedList。实际 90% 用 ArrayList |
| **HashMap 底层** | JDK8+：数组 + 链表 + **红黑树**（链表 >8 且数组 ≥64 树化，<6 退化） |
| **HashMap 扩容** | 默认容量 16，负载因子 0.75，扩容 2 倍（`2^n` 便于位运算定位下标） |
| **HashSet 如何去重** | 基于 HashMap：元素作 key，value 是固定 PRESENT。依赖 `hashCode()` + `equals()` |
| **CHM vs Hashtable** | Hashtable 全表 synchronized；CHM 用 CAS + 节点级 synchronized，并发度更高 |
| **CHM 演进** | JDK7：分段锁 Segment；JDK8：取消分段，CAS + 节点锁 |

### 本项目用到的集合
- `ConcurrentHashMap`：ID 服务的号段缓存、AI 对话的会话上下文
- `AtomicLong`：号段游标、统计计数
- `ArrayList` / `List.of()`：批量 ID、搜索结果
- `LinkedBlockingQueue`：异步预取线程池的任务队列
- `CopyOnWriteArrayList`：知识图谱三元组（读多写少）

## 10. 说一下 CAS

### 是什么
**Compare And Swap（比较并交换）**，乐观锁的核心实现，CPU 原子指令。

### 三要素
```
内存地址 V（要更新的变量）
预期原值 A（Expected）
新值 B（New）

操作：如果 V == A，则把 V 改为 B，返回成功；否则什么都不做，返回失败
```

### Java 中的实现
```java
AtomicLong cursor = new AtomicLong(0);
cursor.compareAndSet(0, 1);      // 期望 0，改成 1
cursor.getAndIncrement();         // 内部就是 CAS 循环
```
底层：`Unsafe` 类 → CPU 指令（x86 的 `cmpxchg`），硬件保证原子性。

### 本项目落点：ID 号段发号

`service-id-generator/SegmentBuffer.Segment.tryNext()`：
```java
public long tryNext() {
    while (true) {
        long cur = cursor.get();
        if (cur > end) return ILLEGAL_ID;                  // 越界，通知切换号段
        if (cursor.compareAndSet(cur, cur + 1)) return cur; // CAS 成功才返回
        // 失败说明被其他线程抢先，继续自旋重试
    }
}
```
**为什么用 CAS**：多线程并发取号，CAS 保证每个 ID 只被一个线程拿到，**不重复、不丢失**，比 `synchronized` 轻量（无内核态切换）。

### CAS 的三个问题

| 问题 | 说明 | 解决 |
|---|---|---|
| **ABA 问题** | 值 A→B→A，CAS 以为没变 | 加**版本号**：`AtomicStampedReference` |
| **自旋开销大** | 竞争激烈时 CPU 空转 | ①JVM 自适应自旋；②`LongAdder` 分散热点；③退化为锁 |
| **只能保证一个变量原子** | 多变量需整体原子 | 封装成对象，用 `AtomicReference` |

### 面试话术
> "CAS 是乐观锁的实现，三个操作数：内存值、预期值、新值，只有内存值等于预期值才更新。Java 里 atomic 包底层用 Unsafe 调 CPU 的 cmpxchg 指令保证原子性。我在 ID 生成服务发号时用 CAS 自增游标，保证多线程下 ID 不重复不丢失，比 synchronized 轻量。它有 ABA（用版本号解决）、自旋开销大（用 LongAdder 分散）、只能保证单变量原子（封装对象用 AtomicReference）三个问题。"

## 11. 说一下 AQS

### 是什么
**AbstractQueuedSynchronizer**，JUC 锁和同步器的**基础框架**。
`ReentrantLock`、`CountDownLatch`、`Semaphore`、`ReentrantReadWriteLock` 都基于它。

### 核心组成

```
1. state（volatile int）              → 同步状态：锁是否被占用 / 资源数量
2. CLH 双向队列（FIFO）               → 抢不到锁的线程排队
3. CAS + LockSupport.park/unpark      → 原子改 state、阻塞/唤醒线程
```

### 工作流程（独占锁）

```
线程 A 获取锁 → CAS 修改 state：0 → 1 → 成功，A 持有锁
                                        │
线程 B 获取锁 → CAS 失败（state 已是 1）
             → 进入 CLH 队列 → LockSupport.park() 挂起
                                        │
线程 A 释放锁 → state 改回 0 → 唤醒队头（unpark）
                                        │
线程 B 被唤醒 → 重新 CAS 获取锁
```

### 两种模式

| 模式 | 说明 | 典型 |
|---|---|---|
| **独占（Exclusive）** | 一次只有一个线程 | `ReentrantLock` |
| **共享（Shared）** | 多线程可同时 | `Semaphore`、`CountDownLatch`、读写锁的读锁 |

### 公平 vs 非公平
- **非公平（默认）**：新线程先尝试插队 CAS，失败才排队 → **吞吐高**，可能饥饿
- **公平**：先检查队列有无等待者，有则排队 → 公平但吞吐低

`new ReentrantLock(true)` 为公平锁。

### 面试话术
> "AQS 是 JUC 同步器的基础框架，ReentrantLock、CountDownLatch、Semaphore 都基于它。核心三部分：volatile 的 state 表示同步状态，CLH 双向队列存放等待线程，用 CAS 改 state、用 LockSupport 阻塞唤醒线程。
>
> 流程是：线程 CAS 改 state 成功就拿到锁，失败就进队列挂起；释放后把 state 改回并唤醒队头节点。它分独占和共享两种模式、公平和非公平两种策略，默认非公平因为吞吐量更高。"

## 12. 线程池的核心参数

### 七大参数

```java
ThreadPoolExecutor(
    int corePoolSize,                  // ①核心线程数：常驻线程
    int maximumPoolSize,               // ②最大线程数：核心 + 临时线程上限
    long keepAliveTime,                // ③临时线程空闲多久后销毁
    TimeUnit unit,                     // ④时间单位
    BlockingQueue<Runnable> workQueue, // ⑤任务队列
    ThreadFactory threadFactory,       // ⑥线程工厂（命名、守护线程）
    RejectedExecutionHandler handler   // ⑦拒绝策略
)
```

### 任务提交的执行顺序（易错点）

```
提交任务
  │
  ├─1 当前线程数 < corePoolSize  → 创建核心线程执行
  │
  ├─2 核心线程已满 → 任务进入队列 workQueue
  │
  ├─3 队列也满了 → 创建临时线程（直到 maximumPoolSize）
  │
  └─4 线程数达最大且队列满 → 执行拒绝策略
```

⚠️ **常见误区**：以为核心线程满了就立即创建临时线程。**实际是先入队列，队列满了才会创建临时线程**。

### 四种拒绝策略

| 策略 | 行为 |
|---|---|
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` |
| `CallerRunsPolicy` | **由提交任务的线程自己执行**（降级，减缓提交速度） |
| `DiscardPolicy` | 静默丢弃 |
| `DiscardOldestPolicy` | 丢弃队列最老的任务，重试提交 |

### 本项目落点：ID 号段异步预取线程池

`service-id-generator/.../IdGeneratorServiceImpl.java` 第 65 行：
```java
prefetchExecutor = new ThreadPoolExecutor(
        properties.getPrefetchPoolSize(),    // 核心=最大=4
        properties.getPrefetchPoolSize(),
        0L, TimeUnit.MILLISECONDS,           // 临时线程不保留
        new LinkedBlockingQueue<>(256),      // 队列容量 256
        r -> {                               // 线程工厂：命名 + 守护线程
            Thread t = new Thread(r, "idgen-prefetch-" + idx.getAndIncrement());
            t.setDaemon(true);
            return t;
        },
        new ThreadPoolExecutor.CallerRunsPolicy()   // 队列满则由业务线程兜底执行
);
```

**设计考量**：
- 核心=最大：预取是轻量任务，固定线程数避免频繁创建销毁
- 队列 256：缓冲突发预取请求
- **自定义线程名**：`idgen-prefetch-N`，排查问题时能从日志/堆栈一眼认出
- **守护线程**：不阻塞 JVM 关闭
- **CallerRunsPolicy**：队列满时由业务线程自己预取，保证号段最终能加载（不丢任务）

### 为什么不用 Executors 创建（阿里规范）

| 方法 | 问题 |
|---|---|
| `Executors.newFixedThreadPool()` | 队列是 `LinkedBlockingQueue` 无界 → **OOM** |
| `Executors.newCachedThreadPool()` | 最大线程数 `Integer.MAX_VALUE` → **创建大量线程 OOM** |
| `Executors.newSingleThreadExecutor()` | 无界队列 → OOM |

**结论**：必须**手动 new ThreadPoolExecutor**，明确队列容量与拒绝策略。

### 线程数怎么定

| 任务类型 | 建议 |
|---|---|
| **CPU 密集型** | `CPU 核数 + 1`（减少上下文切换） |
| **IO 密集型** | `CPU 核数 × 2` 或 `核数 / (1 - 阻塞系数)`（如阻塞 0.9 → 20 倍） |

本项目预取是 **IO 密集型**（查 DB），4 个线程足够（号段是批量申请，不需要很高并发）。

### 面试话术
> "线程池七个核心参数：核心线程数、最大线程数、空闲时间、时间单位、任务队列、线程工厂、拒绝策略。执行顺序要注意：核心线程满了是先入队列，**队列满了才会创建临时线程**，最后才走拒绝策略。
>
> 不用 Executors 创建是因为它用无界队列或最大线程数无限，会导致 OOM，必须手动 new 明确队列容量和拒绝策略。我在 ID 服务异步预取号段时用了固定 4 线程的线程池，自定义线程名便于排查，守护线程不阻塞 JVM 关闭，拒绝策略用 CallerRunsPolicy——队列满时由业务线程自己预取，保证号段一定能加载。"
