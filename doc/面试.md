## 一、简历项目描述（可直接粘贴）

### 分布式 ID 生成服务（service-id-generator）

**技术栈**：Spring Boot 3 + Spring Cloud Alibaba 2022 + MyBatis-Plus + MySQL 8 + Redis + Sentinel 1.8 + Nacos

**项目描述**

独立设计开发分布式 ID 生成微服务，为订单、用户、短剧、评论等业务提供全局唯一主键。解决微服务架构下多服务并发创建数据导致的数据库自增 ID 性能瓶颈与分库分表主键冲突问题。

**核心实现**

- 参考美团 Leaf **号段模式**，采用「MySQL + 号段缓存 + 本地内存发号」：通过 `max_id + step` 批量申请 ID 区间，业务取号时在本地内存原子自增，**不访问数据库**
- 以 `biz_tag` 维度隔离业务号段（order / user / drama / comment 等 12 种），类型安全地通过枚举 `BizTypeEnum` 申请，避免裸字符串传参
- **数据库事务 + 乐观锁**（version 字段）保障号段分配一致性，冲突自动重试 3 次，多实例并发申请到的区间互斥不重叠
- **双 Buffer 异步预取**：当前号段剩余量低于 20% 时，由独立线程池异步加载下一号段，数据库加载耗时不落在业务请求链路上
- **Redis** 记录发号统计与热点 bizTag；**Nacos** 服务注册发现，支持多实例水平扩展
- **Sentinel** 限流 + 降级保护，提供 `/status`、`/metrics`、`/warmUp` 监控端点

**问题排查与优化**

- 修复预取逻辑**同步阻塞**问题：原实现在业务线程内直接查库，违背双 Buffer 设计初衷，改为独立线程池异步预取
- 修复**并发竞态**：原实现 `isExhausted()` 与自增之间无同步，多线程下可能重复发号；改为 `AtomicLong` CAS 取号（越界返回 -1）+ `synchronized` 段切换
- 修复**预取阈值计算错误**：原判断 `cursor > end * 0.8` 在号段起点非 0 时失效，改为按剩余量占比 `remaining / (end - start + 1) <= 20%` 判断
- 提供**批量取号 + 本地 ID 池**方案，将「每单一次远程调用」降为「每 100 单一次」，显著降低网络开销

**设计权衡**

- 降级策略采用**快速失败**（返回 429 / 503 明确错误码）而非返回兜底 ID —— ID 服务一旦妥协返回错误值会直接导致主键冲突

## 二、面试 1 分钟口述稿

### 版本 A：技术深挖版（推荐）

> 我做过一个分布式 ID 生成服务，参考美团 Leaf 的号段模式。核心思路是业务服务取 ID 时不碰数据库——我们从数据库批量申请一个 ID 区间，比如一次拿 1000 个，然后在服务本地内存用原子自增发号，这样访问数据库的次数降低了三个数量级。
>
> 为了保证多实例不冲突，申请号段时用数据库事务加乐观锁，通过 `max_id + step` 分配互斥的连续区间。双 Buffer 方面，当前号段剩余量低于百分之二十时，我用独立线程池异步去预取下一段，这样数据库加载的耗时不会落在业务请求链路上。限流用 Sentinel，降级我做的是快速失败而不是返回兜底 ID，因为返回错误 ID 会直接导致主键冲突。
>
> 过程中我修了三个 bug：一是原来的预取是同步的，业务线程会阻塞在数据库上，等于双 Buffer 白做；二是并发下有竞态，判断耗尽和自增之间没有同步，多线程可能重复发号，我改成 CAS 取号加同步段切换；三是预取阈值判断写错了，原来拿游标和 end 乘零点八比较，号段起点不是 0 的时候就完全失效，我改成按剩余量占比来算。
>
> 另外我还提供了批量取号加本地 ID 池的方案，把每一单一次远程调用降成每一百单一次。

### 版本 B：挑战导向版（被问「最大挑战」时用）

> ID 服务我印象最深的是它第一版看起来能跑，但压测和代码 review 时暴露了三个问题。
>
> 第一个是双 Buffer 形同虚设——预取是同步调用的，业务线程会卡在数据库上，这违背了这个设计本身的目的，我改成独立线程池异步预取才真正生效。
>
> 第二个是并发安全：原来判断号段是否耗尽和自增操作之间没有同步，多线程下可能两个线程同时拿到同一个 ID，这对主键服务来说是致命的。我改成用 AtomicLong 的 CAS 原子取号，越界就返回负一，然后段切换走 synchronized，保证不重复也不丢失。
>
> 第三个比较隐蔽：预取阈值判断写成了游标大于 end 乘零点八，但号段起点如果不是 0 —— 比如从 1001 开始 —— 这个判断就完全失效了，可能剩百分之四十才触发预取。我改成用剩余量占区间长度的比例来判断。
>
> 这几个问题让我意识到，高并发组件里「看起来对」和「真的对」之间差得很远，尤其是边界条件和并发时序，必须靠代码审查和压测去验证。

## 三、追问应对（必背）

| 面试官问 | 你怎么答 |
|---|---|
| **服务重启，号段里没用完的 ID 会怎样？** | 会丢失，ID 不连续。这是 Leaf 号段模式的**已知取舍**——用「ID 不连续」换「高性能」。如果业务要求严格连续（如财务流水对账）就不能用号段模式。**主动承认取舍非常加分** |
| **为什么不直接用雪花算法？** | 雪花依赖机器时钟，**时钟回拨**会产生重复 ID，需要额外处理；号段模式 ID 是**单调递增**的，对 MySQL B+ 树索引更友好、页分裂少。缺点是依赖 DB、ID 不连续。选号段是因为业务能接受不连续，且已有 MySQL 高可用 |
| **发号 QPS 能到多少？** | 业务取号是纯内存 `AtomicLong` CAS，只有号段耗尽/预取时才碰数据库，step=1000 意味着约 **1000 次请求才 1 次 DB 访问**。（⚠️ 别说「万级 QPS」，除非你真压测过） |
| **异步预取失败怎么办？** | `needPrefetch` 标志恢复为 true 等待下次重试；若 next 未准备好，取号走**同步兜底**加载——正确性优先于延迟，宁可慢也不能发错号 |
| **降级为什么不用兜底值？** | ID 服务妥协返回错误值会造成**主键冲突**，比「不可用」更严重。所以用快速失败 + 明确错误码（429 限流 / 503 降级），压力交给上游熔断 |
| **怎么防止单实例打垮号段数据库？** | Sentinel 限流（默认 `/next` 2 万 QPS）+ 批量取号减少远程调用 + 调大 step 降低 DB 访问频率 |
| **ID 会用完吗？** | BIGINT 上限 9.2e18，按每天 1 亿 ID 算可用约 250 万年，不用担心 |
| **多实例如何保证不重复？** | 乐观锁 version 更新 max_id，冲突自动重试 3 次，每个实例拿到互斥的连续区间 |
| **号段步长怎么定？** | 权衡：step 越大 DB 访问越少，但重启时浪费的 ID 越多。一般按「QPS × 可接受重启浪费时长」估算，默认 1000 |

## 五、⚠️ 诚信提醒（重要）

文档中的量化数据请**实测后再填**，否则面试官一问就穿帮：

1. **QPS 数字**：「step=1000 意味着约 1000 次请求 1 次 DB 访问」是**逻辑推导**，可放心说；但「实测万级 QPS」必须真跑过才能说。

2. **建议真跑一次压测**：加一个并发测试验证「10 线程 × 10 万次取号零重复」，跑通后可以 confidently 说：
   > "我压测过，10 线程并发取 10 万次 ID，零重复，平均耗时 XX 毫秒"

   这句话比任何形容词都有说服力。

3. **「独立开发」的表述要诚实**：如果是基于团队已有代码重构，就说「**主导重构**」而非「独立设计开发」。面试时讲「我在原有实现上发现并修复了三个问题」反而更真实、更显能力。

## 六、调用方接入示例（order 服务）

```java
// 1) 注入 Feign Client（已在 common-feign 定义好契约）
private final IdGeneratorFeignClient idGeneratorClient;

// 2) 启动类开启 Feign 扫描
@EnableFeignClients(basePackages = "com.bunny.flix")

// 3) 取号（务必校验 code == 200，因为有限流 429 / 降级 503）
Result<Long> res = idGeneratorClient.nextId(BizTypeEnum.ORDER);
if (res == null || res.getCode() == null || res.getCode() != 200) {
    throw new RuntimeException("获取订单ID失败: " + (res == null ? "无响应" : res.getMessage()));
}
Long orderId = res.getData();
```

**注意**：Feign 走服务名直连（Nacos + LoadBalancer），**不经过 Gateway**，因此无需 token，但 ID 服务内 `UserContext.getUserId()` 为 null（无 `X-User-Id` 透传）。

## 一、简历项目描述（可直接粘贴）

### 短剧播放微服务（Drama Play Service）

**技术栈**：Spring Boot 3 + Spring Cloud Alibaba + MyBatis-Plus + MySQL 8 + Redis + RocketMQ + Sentinel + Nacos + HLS

**项目描述**

设计并开发独立的短剧播放微服务，负责播放链路管理、播放鉴权、视频地址管理、观看进度记录、播放行为采集与事件分发。支撑海量用户并发观看，并通过金币激励、行为分析提升用户留存。

**核心实现**

- **播放入口**：`GET /api/play/{episodeId}` 聚合「查剧集 → 校验权限 → 生成凭证 → 返回 CDN 地址」全流程
- **播放安全（防盗链）**：生成临时播放凭证 `MD5(userId|episodeId|expireTime|secret)`，播放地址拼接 `token` 与 `expire` 参数，CDN 回源校验签名与过期时间，防止用户复制裸地址传播
- **HLS 流媒体**：视频转码切片为 `index.m3u8 + .ts` 分片，支持分片加载、断点续播、CDN 缓存与动态码率
- **观看进度**：实时进度写 Redis（`watch:{userId}:{episodeId}`），由定时任务**分钟级批量同步**到 MySQL，将高频写转换为低频批量写
- **行为采集与事件分发**：采集 `PLAY_START / PLAY_PAUSE / PLAY_PROGRESS / PLAY_COMPLETE` 四类事件，经 RocketMQ 异步投递给金币、推荐、用户画像、数据统计服务
- **金币奖励（service-coin）**：独立金币服务消费 `PLAY_COMPLETE` 事件发放奖励，采用 **Redis SETNX 双端幂等 + 数据库唯一索引**三道防线防重复发币；余额更新使用乐观锁，并配置每日限额防刷
- **热点缓存与击穿防护**：`drama:detail:{id}` 采用 Cache-Aside 策略，缓存失效时用**分布式锁**保证单线程回源；TTL 加随机抖动防止缓存雪崩
- **服务保护**：Sentinel 对播放接口限流（5 万 QPS），超阈值限流、异常降级

**技术亮点**

- **高并发**：Redis 承载实时进度与热点数据、CDN 分发视频流、批量落库降低 DB 压力
- **高可靠**：RocketMQ 异步解耦，埋点失败不影响用户观看；消息幂等处理
- **高扩展**：微服务拆分 + 事件驱动架构，新增下游消费者无需改动播放服务

## 二、面试 1 分钟口述稿

> 我做的是短剧播放微服务，核心是播放链路。用户请求 `GET /api/play/{episodeId}`，服务先查剧集信息（走缓存），校验权限，然后生成一个临时播放凭证——用 MD5 对用户 ID、剧集 ID、过期时间和密钥签名，拼到 CDN 地址上做防盗链，这样用户就算复制地址，过期或者被篡改也播不了。
>
> 视频用 HLS 协议，转码切成 m3u8 加多个 ts 分片，天然支持分片加载、断点续播和 CDN 缓存。
>
> 高并发这块我主要解决两个问题。第一个是观看进度：如果每秒都写数据库，百万用户会带来巨大的写压力，所以我把实时进度写到 Redis，再由定时任务分钟级批量同步到 MySQL，把高频写变成了低频批量写。第二个是热点剧集的缓存击穿：热点 Key 失效的瞬间如果百万并发直接落到数据库会打挂它，我用分布式锁保证只有一个线程回源，其他线程等一会儿重读缓存，同时 TTL 加了随机抖动防止集体失效造成雪崩。
>
> 行为采集方面，我采集开始、暂停、进度、完成四类事件，通过 RocketMQ 异步发给金币、推荐、画像这些下游服务。这里有个坑是 MQ 可能重复投递，导致重复发金币，所以我用 Redis 的 SETNX 做幂等标记，抢到才发，重复请求直接拦截。
>
> 另外埋点失败我做了降级——只记日志，绝不能因为埋点失败影响用户正常播放。

## 三、追问应对（必背）

| 面试官问 | 你怎么答 |
|---|---|
| **百万用户同时观看怎么抗压？** | 分三层：①视频流走 CDN，不占应用服务器带宽；②热点数据（剧集详情、进度）走 Redis；③数据库写入由「实时写」改「批量写」，定时任务分钟级同步 |
| **缓存穿透/击穿/雪崩分别怎么解决？** | 穿透：空值缓存 + 参数校验；击穿：热点 Key 用**分布式锁**单线程回源；雪崩：TTL 加**随机抖动**避免同时失效。我在播放服务里重点处理了击穿和雪崩 |
| **为什么进度不直接写 MySQL？** | 100 万用户 × 每 5 秒上报 = 20 万 QPS 写库，行锁争用严重。改用 Redis 承接实时态 + 定时批量落库，写压力降低两个数量级。代价是进度允许少量丢失（宕机时最多丢一个同步周期的数据），这个取舍对观看进度场景是可接受的 |
| **MQ 重复消费怎么办？** | 两层防护：①入口用 Redis SETNX 做幂等抢占（快，挡掉大部分重复）；②消费端按唯一键去重。SETNX 的 TTL 设为 30 天，覆盖活动周期 |
| **播放 Token 被截获怎么办？** | Token 与 userId 绑定（签名含 userId），换用户无效；有效期 10 分钟，过期自动失效；生产可叠加 IP 绑定、Referer 校验、URL 时效更短（如 2 分钟） |
| **Token 为什么用 MD5 而不是 JWT？** | 播放凭证是给 CDN 边缘节点校验的，要求**极轻量**、无状态、计算快；MD5 签名足够，且不需要 JWT 的完整载荷与解析开销。JWT 更适合需要携带用户信息的业务鉴权 |
| **Redis 挂了怎么办？** | 分层降级：进度写 Redis 失败只记日志不影响播放（进度允许丢）；缓存读取失败降级回源 DB；但**金币幂等标记写入失败时我选择拒绝发放**——宁可不发，不可重复发 |
| **keys 命令有什么问题？** | `keys` 会阻塞 Redis 单线程，大数据量下造成服务抖动。我在同步任务里用了 `keys`，**这是个已知隐患，生产应改 `SCAN` 游标遍历**（主动说出来加分） |
| **断点续播怎么实现？** | 播放接口返回 `lastPosition`（从 Redis 读上次进度），前端拿到后设置 `video.currentTime` 从该位置继续播 |
| **为什么用 HLS 不用 MP4？** | HLS 支持分片加载（边下边播）、动态码率（根据网速切清晰度）、CDN 缓存友好；MP4 需要完整下载 metadata 才能播，首帧慢 |
| **MQ 重复消费，光靠 Redis SETNX 够吗？** | **不够**。SETNX 有过期时间，极端情况会失效；且 Redis 故障时不可用。所以必须加**数据库唯一索引**做最终兜底，这才是幂等的最后防线 |
| **余额并发更新怎么保证不错乱？** | 账户表加 `version` 乐观锁，更新时 `WHERE version = 旧值`，失败重试 3 次。比 `UPDATE balance = balance + x` 更安全吗？其实 InnoDB 的行锁已能保证原子性，但乐观锁能防止**读后写**之间的丢失更新，且便于做重试与冲突监控 |
| **消费端抛异常会怎样？** | RocketMQ 会**无限重试**（默认 16 次后进入死信队列），大量失败会造成消息堆积雪崩。所以我在消费端 catch 所有异常只记日志，配合幂等保证数据正确 |
| **每日限额怎么实现？** | Redis 计数 `coin:daily:{userId}:{date}`，过期时间设为**当日 23:59:59**，跨自然日自动失效，无需额外清理任务 |

## 一、简历项目描述（可直接粘贴）

### 短剧搜索服务（service-search）

**技术栈**：Spring Boot 3 + Elasticsearch 8.14 + Redis + RocketMQ + MyBatis-Plus

**项目描述**

基于 Elasticsearch 搭建短剧搜索服务，支撑剧名、演员、题材、标签等多字段检索，并保障搜索接口的高性能与索引数据的最终一致。

**核心实现**

- **索引设计**：针对剧名、简介、演员、标签等字段设计 Mapping，中文使用 **IK 分词器**（索引 `ik_max_word` / 查询 `ik_smart`），并为 `tags`、`category` 等字段保留 `keyword` 子字段以支持精确筛选与聚合；分片数按数据量规划，并调大 `refresh_interval` 提升写入吞吐
- **检索能力**：全文检索用 `multi_match`（best_fields）跨字段加权（剧名权重最高）；题材、标签、播放量等筛选条件放 **filter 上下文**——不参与算分且结果可被 ES 缓存，性能明显优于 must
- **相关性排序**：默认排序用 **function_score** 把热度、播放量以 `Log1p` 平滑后加权到相关度得分，实现「相关度 + 热度」混合排序，而非单纯按时间倒序
- **缓存设计**：热点搜索结果与联想词走 Redis，用**空值缓存**防穿透、**互斥锁**防击穿；排行榜等热点数据用**逻辑过期**保证永不断流；TTL 加随机抖动防雪崩
- **最终一致**：短剧后台变更经 **RocketMQ** 投递 `drama-sync`，搜索服务消费后更新 ES 索引并失效相关缓存，实现 MySQL → MQ → Search → ES 的最终一致；消费端基于**版本号 + Redis 去重**做幂等，避免乱序覆盖与重复消费

## 二、面试 1 分钟口述稿

> 搜索服务我是基于 Elasticsearch 搭的。索引这块，中文分词用的是 IK 插件——索引时用 ik_max_word 做细粒度切分提高召回，查询时用 ik_smart 提高精度；同时给 tags、category 这些字段加了 keyword 子字段，用来做精确筛选和聚合。
>
> 查询方面，全文检索我用 multi_match 跨字段查询并给不同字段配权重，剧名权重最高。筛选条件我特意放在 filter 上下文里，因为它不参与算分，而且 ES 会缓存 filter 的结果，比放在 must 里快。排序上我没有简单按时间倒序，而是用 function_score 把热度和播放量做 Log1p 平滑之后加到相关度得分上，这样既相关又兼顾热度。
>
> 缓存这块我主要解决三个问题：缓存穿透用空值缓存，查不到的数据也缓存一个空标记、TTL 设短一点；缓存击穿用互斥锁，保证热点 key 失效时只有一个线程回源；排行榜这类极热点数据我用的是逻辑过期，把过期时间放在 value 里面，过期后由一个线程异步刷新，其他请求继续返回旧值，做到永不断流。另外 TTL 都加了随机抖动防止雪崩。
>
> 一致性方面，短剧后台改数据后发 RocketMQ，搜索服务消费消息更新 ES 并失效缓存，走的是最终一致。消费端我做了两层防护：一是用 updateTime 版本号丢弃乱序的旧消息，二是用 Redis 去重拦截 MQ 重复投递。

## 三、追问应对（重点）

### 3.1 关于「150ms 响应」

| 追问 | 怎么答 |
|---|---|
| **150ms 是怎么做到的？** | 分两层看：**缓存命中走 Redis，基本在 5ms 内**；未命中才走 ES。ES 侧的优化有四块：①筛选条件放 filter 上下文（不参与算分 + 结果可缓存）；②`_source` 按需裁剪，减少网络传输（列表页不返回 description）；③控制分片数，避免过多分片带来的合并开销；④避免深分页。另外我加了耗时统计和慢查询告警，`/api/search/metrics` 能看到平均耗时、慢查询数和缓存命中率 |
| **你怎么证明真的在 150ms 内？** | 服务里记录了每次 ES 查询耗时，超过阈值会打慢查询日志；`GET /api/search/metrics` 返回 `avgTookMs`、`slowQueryCount`、`cacheHitRate`。**这是可度量的手段，具体数字需要压测后填**（见第五节诚实提醒） |
| **缓存命中率多少？** | 从 metrics 的 `cacheHitRate` 看。命中率上不去的话可以调大 TTL，或者对热点词做预热 |

### 3.2 关于「分词器选型」

| 追问 | 怎么答 |
|---|---|
| **为什么用 IK，不用 ES 默认分词？** | ES 默认的 `standard` 分词器对中文是**按单字切分**，「重生之逆袭」会被切成「重/生/之/逆/袭」，导致：①语义丢失、召回质量差；②倒排索引膨胀、查询变慢。IK 是针对中文的词典分词，能正确切出「逆袭」这类词 |
| **为什么索引用 ik_max_word、查询用 ik_smart？** | 这是经典组合：**索引时细粒度**（ik_max_word，尽可能多切，提高召回率），**查询时粗粒度**（ik_smart，切得少而准，提高精确率）。两者配合在召回和精度之间取平衡 |
| **IK 词典不支持网络新词怎么办？** | IK 支持**扩展词典**（自定义 .dic 文件）和远程词典热更新。短剧标题常有网感词，可以维护业务词库定期更新 |
| **如果 ES 没装 IK 插件会怎样？** | 索引创建会直接失败（mapping 里指定了不存在的 analyzer）。**这是部署一致性问题**——我踩过类似的坑，所以建索引前要先确认插件就绪 |

### 3.3 关于「深分页」

| 追问 | 怎么答 |
|---|---|
| **分页很深会有什么问题？** | `from + size` 模式下，比如 `from=10000, size=10`，协调节点需要向**每个分片**都要 10010 条，然后在内存里排序取前 10。分片越多、翻页越深，内存和 CPU 开销越大。ES 默认 `max_result_window=10000`，超过就报错 |
| **怎么解决？** | 三种方案，按场景选：<br>① **`search_after`**（推荐）：用上一页最后一条的排序值作为游标，无深度限制，适合实时翻页；缺点是不能跳页<br>② **`scroll`**：快照式遍历，适合**全量导出/离线重建索引**，不适合实时请求（占用资源）<br>③ **业务上限制分页深度**：搜索场景用户很少翻到第 100 页，直接限制即可<br>我把 `max_result_window` 调到了 100000 作为过渡，但深分页场景应该用 `search_after` |
| **为什么不用 scroll 做实时搜索？** | scroll 会持有索引快照，长时间占用资源，且数据不是实时的 |

### 3.4 关于「相关性调优」

| 追问 | 怎么答 |
|---|---|
| **相关性怎么调？** | 我用了三层手段：<br>① **字段权重**：`title^3.0 > description^1.5 > actors/tags^1.2`，标题命中比简介命中更重要<br>② **function_score**：把 `heatScore`、`playCount` 用 `Log1p` 平滑后加权到相关度得分上（`boost_mode=sum`）。用 Log1p 是因为播放量可能差异极大（几千到几千万），直接线性加权会让热度完全压倒相关度<br>③ **minimumShouldMatch=75%**：避免长尾词过多导致大量低质量结果被召回 |
| **怎么验证调得对不对？** | 两个手段：①用 ES 的 **`explain` API** 看每个文档的算分明细，确认权重是否符合预期；②看业务指标（搜索结果的点击率、无结果率），线上做 A/B |
| **多字段查询用 bool should 还是 multi_match？** | 我用 `multi_match`（best_fields）。相比 bool should，它写法更简洁，且 ES 对它有专门优化（会把多个字段当作一个整体计算 best 分数），还能配合 `tie_breaker` 让次优字段也贡献部分得分 |

### 3.5 关于「一致性」

| 追问 | 怎么答 |
|---|---|
| **ES 和 MySQL 怎么保持一致？** | **最终一致**，链路是 MySQL → MQ → Search Service → ES。写入 MySQL 后投递消息，搜索服务消费后更新 ES 并失效缓存 |
| **消息丢了怎么办？** | 三层保障：①RocketMQ 自身持久化 + 重试；②消费端不抛异常，失败时清除去重标记以支持重投；③**兜底全量重建**——定期（如凌晨）全量扫描 MySQL 重建 ES 索引，兜住所有漏网之鱼（这是生产必备的补偿机制） |
| **消息乱序导致旧数据覆盖新数据？** | 消费端做**版本号校验**：记录已处理的最新 `updateTime`，收到的消息版本更旧就直接丢弃 |
| **MQ 重复投递？** | Redis SETNX 去重（TTL 与重试窗口匹配），加上 ES 按 doc id 覆盖写本身是幂等的 |
| **为什么用 MQ 而不是直接双写？** | 直接双写会让 ES 写入耦合在业务事务里：ES 抖动会导致主流程失败，且无法保证事务一致性。用 MQ 解耦后，搜索是**旁路**，故障不影响核心业务 |

### 3.6 关于「缓存」

| 追问 | 怎么答 |
|---|---|
| **穿透、击穿、雪崩分别怎么解决？** | 穿透→空值缓存（TTL 更短）；击穿→互斥锁（只有一个线程回源）/逻辑过期（热点永不断流）；雪崩→TTL 随机抖动 |
| **互斥锁和逻辑过期怎么选？** | **互斥锁**适合普通数据，但等待期间线程会阻塞，且有死锁风险；**逻辑过期**适合极热点数据（排行榜），永不阻塞、永远有数据返回，代价是可能短暂返回旧值。我按数据热度分开用 |
| **逻辑过期的 Redis TTL 为什么设成 2 倍？** | 逻辑过期模式下 key **不依赖 TTL 触发失效**，Redis TTL 只是兜底清理（防止 key 永久残留）。设成业务 TTL 的 2 倍，保证"逻辑已过期但异步刷新还没完成"时数据不会被 Redis 清掉 |

```
   ├─2 意图识别 + 工具调用     → lb://bunny-flix-mcp  /api/mcp/call
   │     规则匹配：推荐/类似/榜单/详情/短剧/用户/通知
   │
   ├─3 记录本轮剧名           ConversationContextService.recordDrama()
   │
   └─4 生成回复   LlmService：配了 agent.llm.* 走大模型，否则本地兜底
   ▼
返回 {reply, usedTools, references, resolvedMessage, contextDrama}
```

**并行存在第二套编排**（AI 网关版，偏"检索问答"）：
```
POST /api/aigateway/chat
  → IntentRecognizer（意图分类 RAG/GRAPH/HYBRID/LLM）
  → QueryRouter 分发到 bunny-flix-rag（知识）/ bunny-flix-graph（关系）
  → LlmService 汇总生成
```
两者定位不同：`bunny-flix-agent` 偏**工具调用型对话**，`bunny-flix-aigateway` 偏**知识问答型对话**。

## 四、一次完整请求的处理过程（示例）

**第 1 轮**：用户问「有哪些热门短剧？」

1. `resolveReference()`：无比配指代词 → 原文通过
2. `retrieve("有哪些热门短剧？")` → rag 返回知识片段
3. `decideAndCallTools()`：命中"短剧" → 调 `query_drama`；命中"热门" → 调 `get_hot_ranking`
4. `rememberDrama()`：从工具结果提取首部剧名 **《重生之逆袭人生》** 存入上下文
5. 生成回复，返回 `contextDrama: "重生之逆袭人生"`

**第 2 轮**：用户问「类似刚才那部」

1. `resolveReference()`：命中"刚才那部" → 重写为 **「重生之逆袭人生 类似」**
2. RAG 与工具都用**重写后的语句**检索（关键：否则"刚才那部"检索不到任何东西）
3. `decideAndCallTools()`：命中"类似" → 调 `recommend_drama(keyword=重生之逆袭人生)`
4. 推荐服务按题材"都市励志"找出同类 → 返回《闪婚老公是首富》
5. 更新上下文剧名为本轮结果

**为什么必须做指代消解**：检索层只认具体词，"刚才那部"在短剧库里不存在，不还原就必然空结果。

## 五、⚠️ 两处与描述的真实差距（面试必须如实说）

### 1. 没用 Spring AI，是手写编排

描述写"基于 Spring AI"，实际是**手写 ReAct 风格编排**（`RestTemplate` + 规则匹配），没引入 Spring AI 依赖。

**为什么这么选**（面试这么讲反而是加分）：
> "我当时评估下来，Spring AI 的 `ChatClient`/`function calling` 确实能少写代码，但它绑定了特定的模型抽象，而我们 Agent 的核心诉求是**检索源和工具都可插拔**——RAG、图谱、MCP 工具都是独立微服务，通过 HTTP 调用。手写编排让每一层都能单独替换，不绑死框架。"

**如果要真上 Spring AI**，改造点很明确（可作为"后续优化"讲）：
- 引入 `spring-ai-openai-spring-boot-starter`
- 把 `McpToolService` 的 6 个工具注册为 Spring AI 的 `Function<Request, Response>` Bean
- `AgentService` 改用 `ChatClient` + `.functions(...)` 让模型**自己决定**调哪个工具，替代现在的关键词规则匹配

### 2. RAG 用的是词频向量，不是真 Embedding

`RagService.vectorize()` 是 **字符 2-gram 词频 + 哈希到 1024 维 + 余弦相似度**，没有调用 Embedding 模型。

**面试说法**：
> "向量检索这块我做了分层：内存版用 TF + 余弦相似度，保证不依赖任何外部组件也能跑通全链路；生产环境可以平滑替换成 Milvus + Embedding API，因为 `ingest`/`retrieve` 两个方法的接口是稳定的，换实现不动上层。"

**升级路径**（可作为演进计划讲）：
1. 引入 `milvus-sdk-java`，`RagService` 内部改为写 Milvus collection
2. 加 `EmbeddingClient` 调 Embedding HTTP API 生成向量
3. 切片用**结构化切分**（一条短剧简介 = 一个 chunk），保证召回语义完整

## 六、面试 1 分钟口述稿

> 短剧 AI 对话我做了五个服务：agent 做编排，mcp 提供工具，rag 做知识检索，graph 做关系查询，aigateway 是另一套偏知识问答的编排入口。
>
> 一次对话进来，agent 先做**多轮上下文的指代消解**——用户说"类似刚才那部"，我会把它还原成上一轮提到的具体剧名，再拿去检索；否则检索层根本认不出"刚才那部"是什么。然后并行做两件事：一是调 RAG 做语义检索，二是按意图识别决定调哪个工具。工具我把短剧搜索、详情、热门榜单、相似推荐这些都封装成了 MCP 工具，由 Agent 根据用户意图动态调用。最后把检索结果和工具结果一起交给大模型汇总，没配大模型就走本地兜底，保证离线可跑。
>
> 这里有个设计取舍我要说明：**我没用 Spring AI，而是手写编排**。因为我们的检索源和工具都是独立微服务，手写能让每一层独立替换，不绑死框架。RAG 的向量检索也是分层的——内存版用 TF 加余弦相似度保证全链路能跑通，生产可以平滑换成 Milvus 加 Embedding API，因为 ingest 和 retrieve 的接口是稳定的。

## 七、追问应对

| 追问 | 怎么答 |
|---|---|
| **多轮上下文怎么存的？** | 两层：①短期——前端每轮把最近 10 条历史随请求带上；②指代消解用的"上一部剧名"——服务内存 `ConcurrentHashMap<userId, State>`，30 分钟过期。生产应换 Redis 支持多实例共享（我代码里标注了） |
| **为什么指代消解不用大模型做？** | 规则方案零成本、零延迟、可解释，覆盖"上一部/那部/类似的"这些高频表达已经够用；长尾表达可以再交给大模型兜底。这是**成本与效果的权衡** |
| **工具调用为什么用规则而不是 function calling？** | 规则型意图识别**确定性高、无额外 token 成本、可解释、易排查**；缺点是长尾泛化差。开了 LLM 之后可以升级成 function calling，让模型自己选工具（我在代码注释里标了这个演进点） |
| **Agent 响应慢怎么优化？** | 现在 RAG 和工具调用是**串行**的，可以改成并行（`CompletableFuture`）；另外工具结果可以按 bizTag 缓存 |
| **下游 rag/mcp 挂了怎么办？** | 全部 try/catch 降级：RAG 失败返回空列表、工具失败记录 error，都**不影响主流程返回**——宁可答案简陋，也不能让用户拿不到回复 |
| **Agent 怎么防止被恶意刷？** | 现在网关层有 Sentinel 限流（agent 服务也加载了规则）；生产还应加单用户 QPS 限制和 token 消耗上限 |

# 分布式事务（Seata TCC）—— 购买 VIP 场景

> 模块：`service-member`
> 模式：Seata **TCC**（非 AT），已处理幂等、空回滚、防悬挂三大坑

---

## 一、用在哪里

**场景：购买 VIP 会员**，跨三个资源：

| 资源 | 操作 |
|---|---|
| 用户钱包 `t_user_wallet` | 扣款 |
| VIP 订单 `t_vip_order` | 状态流转 |
| 会员记录 `t_vip_record` | 开通/续期 |

**为什么需要分布式事务**：钱包扣款和开通 VIP 必须**同时成功或同时失败**。只靠本地事务，在微服务多实例 + 后续分库场景下无法保证；只靠 MQ 最终一致，则无法做到"余额不足立即失败"的强一致校验。

---

## 二、TCC 三阶段实现

| 阶段 | 操作 | 代码位置 |
|---|---|---|
| **Try** | 校验余额 → **冻结**金币（`balance - amount`，`frozen_balance + amount`） | `VipPurchaseTccServiceImpl.tryPurchase()` |
| **Confirm** | 扣减冻结额 → 开通 VIP → 订单置已完成 | `.confirmPurchase()` |
| **Cancel** | **解冻**金币 → 订单置已取消 | `.cancelPurchase()` |

**入口**：`VipServiceImpl.purchaseVip()` 标注 `@GlobalTransactional(name="purchase-vip")`

**关键设计**：不直接扣款，而是先**冻结**——预留资源，避免并发下超扣。

---

## 三、TCC 三大坑（面试必问，本项目已处理）

| 坑 | 场景 | 本项目解法 |
|---|---|---|
| **幂等** | Confirm/Cancel 被重复调用 | 用**订单状态**去重：已 Confirm（status=1）或已 Cancel（status=2）则直接返回成功 |
| **空回滚** | Try 未执行却收到 Cancel | 判断 status ≠ 3（未 Try），**只置订单为取消，绝不解冻**——否则会凭空给用户加钱 |
| **防悬挂** | Cancel 先于 Try 到达（网络延迟） | Try 执行前检查 status == 2（已取消）则**拒绝执行**——否则冻结金额永远无 Cancel 释放 |

**状态机**（这是三大坑能解决的关键）：

```
0 待支付 ──Try──> 3 处理中(已冻结) ──Confirm──> 1 已完成
   │                    │
   └──Cancel(空回滚)────┴──Cancel──> 2 已取消
```

通过判断当前状态，就能知道「Try 到底执行过没有」「二阶段是否重复执行」。

---

## 四、面试 1 分钟口述稿

> 分布式事务我用在**购买 VIP** 这个场景，涉及钱包扣款、订单状态、会员开通三个资源，用的是 **Seata 的 TCC 模式**。
>
> 流程是：Try 阶段先**冻结**用户金币做资源预留，而不是直接扣款；全局事务提交后，Seata 自动回调 Confirm 扣减冻结额并开通会员；如果任一步失败，就回调 Cancel 解冻金币。
>
> TCC 有三个经典坑我都处理了：**幂等**用订单状态去重，避免重复开通会员；**空回滚**是 Try 没执行却收到 Cancel，这时候绝对不能解冻，否则会凭空给用户加钱；**防悬挂**是 Cancel 比 Try 先到，这时候 Try 必须拒绝执行，否则冻结的金额再也没有 Cancel 来释放。这三个都是靠订单状态机判断的。
>
> 另外余额更新我用了乐观锁，扣款失败会抛异常让 Seata 重试，因为 Confirm/Cancel 失败如果不重试就会造成资损。

## 五、追问应对

| 追问 | 怎么答 |
|---|---|
| **TCC 和 AT 模式怎么选？** | AT 无侵入（自动生成反向 SQL），但**全程持有全局锁**，高并发热点账户性能差，且有 SQL 支持限制；TCC 性能高（只冻结，锁粒度小）、可控，但要手写三个方法。VIP 购买涉及资金，对一致性和性能都敏感，所以选 TCC |
| **为什么不用 2PC/XA？** | XA 是**资源层**强一致，全程持有数据库锁直到全局提交，并发下性能极差，不适合互联网场景 |
| **Confirm 失败怎么办？** | Seata 会**持续重试**（有重试次数与告警）。所以 Confirm 必须幂等，且失败要抛异常让 TC 感知——绝对不能吞异常，否则资损 |
| **冻结的金额一直没 Confirm/Cancel 怎么办？** | 靠 Seata TC 的事务恢复机制兜底；另外生产应加**对账任务**，扫描长时间处于「处理中」的订单进行补偿 |
| **@GlobalTransactional 和 @Transactional 什么关系？** | `@GlobalTransactional` 是 Seata 的 TM 入口，开启全局事务；内部的 `@Transactional` 是本地事务（分支）。二者配合，全局事务协调各分支的提交/回滚 |
| **Seata 挂了怎么办？** | TC 是单点风险，生产要部署**集群 + DB 存储模式**（global_table/branch_table），保证 TC 高可用 |
