# 短剧搜索服务 —— 逐句拆解（流程 + 代码支撑）

> 模块：`service-search`（端口 8400）
> 技术栈：Elasticsearch 8.x(Java API Client) + Redis + RocketMQ + MyBatis-Plus
> 每句给出：**业务含义 → 处理流程 → 代码支撑（精确到方法/行号）→ 面试话术**

## 第 1 句

> **「基于 Elasticsearch 搭建短剧搜索服务：针对剧名、演员、题材、标签等字段设计 Mapping 及索引，实现全文检索、多条件筛选及相关性排序；支撑短剧/剧集文档检索，通过优化分词、Mapping 及查询条件，将搜索接口响应控制在 150ms 以内」**

### 业务含义
用户找剧靠搜索。要支持模糊搜索（"重生逆袭"）、按条件筛（题材/标签/播放量）、结果按相关度排，并且要快。

### 处理流程
```
GET /api/search?keyword=重生
  │
  ▼ SearchController.search()
SearchServiceImpl.advancedSearch()     第 130 行
  ├─ 构建缓存 key                       第 465 行
  ├─ 查 Redis（命中直接返回）            SearchCacheService 第 74 行
  ├─ 未命中 → doSearch()                第 164 行
  │     ├─ buildQuery()  全文 + 筛选    第 218 行
  │     ├─ ES 查询 + 高亮
  │     └─ recordLatency() 耗时统计     第 455 行
  └─ 写回缓存
```

### 代码支撑

#### ① Mapping 设计（含优化点）— 第 62 行 `DRAMA_INDEX_JSON`
```json
{
  "settings": {
    "number_of_shards": 3,          // 第 65 行：从 1 改为 3
    "number_of_replicas": 1,
    "refresh_interval": "5s"        // 调大 → 降低段合并频率，提升写入吞吐
  },
  "mappings": {
    "properties": {
      "title": { "type": "text", "analyzer": "ik_max_word", "search_analyzer": "ik_smart",
                 "fields": { "keyword": { "type": "keyword" } }, "copy_to": "searchText" },
      "description": { "type": "text", "analyzer": "ik_max_word", "search_analyzer": "ik_smart", ... },
      "actors": { "type": "text", ..., "fields": { "keyword": { "type": "keyword" } } },
      "tags":   { "type": "text", ..., "fields": { "keyword": { "type": "keyword" } } },
      "category": { "type": "keyword" },
      "status":   { "type": "keyword" },
      "searchText": { "type": "text", "analyzer": "ik_max_word" }   // copy_to 汇总
    }
  }
}
```

**Mapping 的 3 个优化点**：
1. **分片数 1 → 3**：单分片数据量过大会显著拖慢查询
2. **`refresh_interval: 5s`**：搜索场景可容忍 5 秒延迟，换来更高写入吞吐
3. **`keyword` 子字段**：`tags`/`actors`/`category` 保留 keyword，才能做**精确筛选与聚合**（text 字段无法 term 查询）

#### ② 全文检索（多字段加权）— `buildQuery()` 第 218 行
```java
Query fullText = MultiMatchQuery.of(m -> m
        .query(query.getKeyword())
        .fields("title^3.0", "description^1.5", "actors^1.2", "tags^1.2", "searchText^0.5")
        .type(TextQueryType.BestFields)
        .minimumShouldMatch("75%"))._toQuery();
```
- **`multi_match` 而非 bool should**：ES 对 multi_match 有专门优化，写法也更简洁
- **字段权重**：剧名命中比简介命中更重要
- **`minimumShouldMatch: 75%`**：避免长尾词过多召回低质量结果

#### ③ 多条件筛选（filter context）— `buildQuery()` 第 218 行
```java
List<Query> filters = new ArrayList<>();
if (category != null) filters.add(TermQuery.of(t -> t.field("category")...));
if (tags != null)     filters.add(TermsQuery.of(t -> t.field("tags.keyword")...));
if (minPlayCount != null) filters.add(RangeQuery.of(r -> r.field("playCount").gte(...)));
return BoolQuery.of(b -> b.must(fullText).filter(filters))._toQuery();
```
**为什么放 filter 而不是 must**：filter **不参与算分**，且 ES 会缓存 filter 结果（query cache），性能明显更好。

#### ④ 相关性排序（相关度 + 热度混合）— 第 218 行
```java
Query scored = FunctionScoreQuery.of(fs -> fs
        .query(fullText)
        .functions(f -> f.fieldValueFactor(fv -> fv
                .field("heatScore").factor(1.2f)
                .modifier(FieldValueFactorModifier.Log1p).missing(0.0)))
        .functions(f -> f.fieldValueFactor(fv -> fv
                .field("playCount").factor(0.8f)
                .modifier(FieldValueFactorModifier.Log1p).missing(0.0)))
        .boostMode(FunctionBoostMode.Sum))._toQuery();
```
**为什么用 `Log1p` 平滑**：播放量从几千到几千万差异极大，线性加权会让热度**完全压倒相关度**；取对数后热度只作为温和加分项。

排序字段映射 — `sortField()` 第 280 行：`heat`/`newest`/`play`/`_score`

#### ⑤ 150ms 的可度量手段 — `recordLatency()` 第 455 行 + `metrics()` 第 433 行
```java
if (tookMs > slowQueryThresholdMs) {   // 默认 150ms
    slowQueryCount.incrementAndGet();
    log.warn("[search] 慢查询告警 took={}ms 超过阈值 {}ms", tookMs, slowQueryThresholdMs);
}
```
`GET /api/search/metrics` 返回：`avgTookMs`、`slowQueryCount`、`cacheHitRate`

### 面试话术
> "索引这块，中文分词用 IK——索引时 ik_max_word 做细粒度切分提高召回，查询时 ik_smart 提高精度；同时给 tags、category 加了 keyword 子字段做精确筛选。查询用 multi_match 跨字段带权重，剧名权重最高；筛选条件我特意放 filter 上下文，因为它不算分而且 ES 会缓存结果。排序上我没简单按时间倒序，而是用 function_score 把热度和播放量做 Log1p 平滑后加到相关度上——用 Log1p 是因为播放量差异极大，线性加权会让热度压倒相关度。"

## 第 2 句

> **「使用 Redis 缓存热门短剧、排行榜等热点数据，结合空值缓存、逻辑过期及互斥锁解决缓存穿透、缓存击穿问题」**

### 业务含义
热点数据（热门搜索词结果、排行榜）走 Redis，并处理三个经典缓存问题。

### 处理流程（两种策略分开用）

```
【普通搜索】queryWithPassThrough()   第 74 行
  查缓存 → 命中（含空值）返回
        → 未命中抢互斥锁 → 回源 → 写缓存 → 释放锁
        → 抢锁失败：等待重试读缓存（不回源）

【排行榜】queryWithLogicalExpire()   第 137 行
  缓存不存在 → 同步回源并写入
  命中未逻辑过期 → 直接返回
  命中已逻辑过期 → 抢锁异步刷新，本次先返回旧值（永不阻塞）
```

### 代码支撑

#### ① 空值缓存（防穿透）— 第 39 行 `EMPTY_MARK`，写入第 122 行
```java
private static final String EMPTY_MARK = "__EMPTY__";
// 回源结果为空时，缓存空标记（TTL 2分钟，比正常缓存短）
if (data == null || isEmptyList(data)) {
    safeSet(key, EMPTY_MARK, emptyTtlMinutes, TimeUnit.MINUTES);
    return CacheResult.empty();
}
```
**为什么能防穿透**：查询不存在的数据时，若不缓存，每次请求都会打到 ES；缓存空值后直接返回。

#### ② 互斥锁（防击穿）— `tryLock()` 第 229 行
```java
Boolean ok = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, "1", LOCK_TTL_SECONDS, TimeUnit.SECONDS);
```
配合**双重检查**（回源前再读一次缓存）与**等待重试**（抢锁失败不回源，等 50ms 重读）

#### ③ 逻辑过期（热点永不断流）— 第 137 行
```java
// 缓存值内嵌逻辑过期时间
public static class LogicalCacheValue<T> {     // 第 300 行
    private T data;
    private long expireAt;
    public boolean isExpired() { return System.currentTimeMillis() >= expireAt; }
}

// 已逻辑过期：抢锁异步刷新，其余请求返回旧值
if (tryLock(lockKey)) {
    rebuildExecutor.submit(() -> {
        T fresh = loader.get();
        safeSet(key, JSONUtil.toJsonStr(newValue), logicalTtlMinutes * 2, TimeUnit.MINUTES);
    });
}
return CacheResult.of(data, true);   // 先返回旧值
```

**Redis TTL 为什么设成逻辑 TTL 的 2 倍**（易被追问）：
> 逻辑过期模式下 key **不依赖 TTL 触发失效**，Redis TTL 只是兜底清理。设 2 倍是为了保证"逻辑已过期但异步刷新还没完成"时数据不会被 Redis 清掉。

#### ④ 排行榜走逻辑过期 — `queryRanking()` 第 193 行 → `hotRanking()` 第 338 行

#### ⑤ 防雪崩 — `randomTtl()` 第 280 行
```java
return baseMinutes + (long) (Math.random() * 5);   // TTL 加 0~5 分钟随机抖动
```

#### ⑥ 缓存失效 — `evictByPrefix()` 第 206 行（索引更新后调用）

#### ⑦ 降级 — 所有 Redis 操作 try/catch，失败降级回源，**不阻断搜索主流程**

### 面试话术
> "缓存我主要解决三个问题：穿透用空值缓存，查不到的数据也缓存一个空标记、TTL 设短一点；击穿用互斥锁，保证热点 key 失效时只有一个线程回源；排行榜这类极热点数据我用逻辑过期，把过期时间放在 value 里面，过期后由一个线程异步刷新，其他请求继续返回旧值，做到永不断流。另外 TTL 都加了随机抖动防雪崩。"

**追问：互斥锁和逻辑过期怎么选？**
→ 互斥锁适合普通数据（等待期间线程阻塞）；逻辑过期适合极热点（永不阻塞，代价是短暂返回旧值）。我按数据热度分开用。

## 第 3 句

> **「基于 RocketMQ 解耦短剧后台与 Elasticsearch 索引更新，通过 MySQL → MQ → Search Service → ES 实现业务数据与搜索索引的最终一致」**

### 业务含义
短剧后台改了数据，ES 索引要跟着更新。不能双写（耦合 + 事务问题），用 MQ 解耦。

### 处理流程
```
MySQL 数据变更
   │ 投递 drama-sync 消息（DramaDTO）
   ▼
RocketMQ
   │
   ▼ DramaSyncConsumer.onMessage()      第 42 行
     ├─1 版本号校验 isStale()           第 77 行（丢弃乱序旧消息）
     ├─2 去重 markProcessed()           第 96 行（SETNX 拦截重复投递）
     └─3 searchService.syncDramaToES()  第 357 行
           ├─ 写入 ES
           └─ 失效相关缓存 evictByPrefix()   第 206 行
```

### 代码支撑

#### ① 消费入口 — `onMessage()` 第 42 行
```java
@RocketMQMessageListener(topic = "drama-sync", consumerGroup = "service-search-drama-sync")
public void onMessage(DramaDTO dramaDTO) {
    if (isStale(dramaId, dramaDTO.getUpdateTime())) return;   // 版本过期，丢弃
    if (!markProcessed(dramaId, dramaDTO.getUpdateTime())) return;  // 重复消息，拦截
    searchService.syncDramaToES(dramaDTO);
}
```

#### ② 版本号校验（防乱序覆盖）— `isStale()` 第 77 行
```java
String cached = redisTemplate.opsForValue().get(versionKey);
LocalDateTime lastVersion = LocalDateTime.parse(cached);
return updateTime.isBefore(lastVersion);   // 消息比已处理的旧 → 丢弃
```
**为什么必要**：MQ 不保证严格顺序，若旧消息后到，会用旧数据覆盖新数据。

#### ③ 去重（防重复投递）— `markProcessed()` 第 96 行
```java
Boolean ok = redisTemplate.opsForValue()
        .setIfAbsent(dedupKey, "1", DEDUP_TTL_MINUTES, TimeUnit.MINUTES);
// TTL 与 MQ 重试窗口匹配
```
失败时 `clearProcessed()` 第 116 行清除标记，允许重试。

#### ④ 写 ES + 失效缓存 — `syncDramaToES()` 第 357 行
```java
elasticsearchClient.index(i -> i.index(DRAMA_INDEX)
        .id(String.valueOf(dramaDTO.getId())).document(sourceMap));
// 索引更新后失效相关缓存，保证搜索结果最终一致
cacheService.evictByPrefix("search:q:");
cacheService.evict("search:ranking:hot:10", "search:ranking:hot:20");
```

#### ⑤ 不抛异常策略 — `onMessage()` 内 catch 所有异常只记日志
**原因**：RocketMQ 会无限重试（默认 16 次后进死信），大量失败会造成消息堆积雪崩。

### 面试话术
> "一致性走的是最终一致：MySQL 改完发 RocketMQ，搜索服务消费后更新 ES 并失效缓存。消费端我做了两层防护——一是用 updateTime 版本号丢弃乱序的旧消息，防止旧数据覆盖新数据；二是用 Redis SETNX 去重拦截 MQ 重复投递。另外消费失败我不抛异常，因为 RocketMQ 会无限重试导致消息堆积，只记日志配合重试机制。"

**追问：消息丢了怎么办？**
→ 三层保障：①RocketMQ 持久化+重试；②失败清除去重标记支持重投；③**兜底全量重建**——定期全量扫 MySQL 重建 ES 索引（生产必备补偿机制）。

**追问：为什么用 MQ 而不是双写？**
→ 双写会把 ES 抖动传导到主流程（ES 故障导致业务写入失败），且无法保证事务一致；MQ 解耦后搜索是**旁路**，故障不影响核心业务。

## 五、面试必记的 3 个"坑"（体现真实性）

| 坑 | 说明 |
|---|---|
| **IK 插件未安装** | Mapping 指定了 analyzer，插件没装会导致**建索引直接失败**（部署一致性问题） |
| **强制 status filter 会让老数据搜不到** | 存量索引的老文档没有 status 字段，加 `status=ONLINE` 过滤会导致历史数据全部搜不到（我已避开，代码里有注释） |
| **`keys` 命令阻塞 Redis** | `evictByPrefix` 用了 `keys`，生产应改 `SCAN` 游标遍历（主动说出是加分项） |
